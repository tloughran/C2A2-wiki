### Sources

1. **Lost-update anomaly and optimistic concurrency control** (Vlad Mihalcea, "A beginner's guide to database locking and the lost update phenomena"; abstractalgorithms.dev, "Lost update explained: when two writes become one"; Scaler, "Lost update problem in DBMS"). [verified this run — snippet level, practitioner and educational sources] — The reframe that challenges the item's chosen remedy. "A lost update occurs when one transaction overwrites the update of another one, causing data loss, typically occurring in a concurrent environment when a transaction follows a **read-modify-write** cycle." Both runs read `needs_review`, formed a disposition, and wrote — a textbook read-modify-write on shared state with no coordination. The standard fix is not a protocol and not a lock: "optimistic locking can replace pessimistic locking, using a **versioning** concurrency control model that works **without acquiring additional write locks**, with a version column ... using the load-time version in the `WHERE` clause." Under that scheme the second run's write would simply have failed, at which point it re-reads, sees the escalation, and either defers or supersedes *knowingly*. One version field, no new authority rules.
2. **Last-writer-wins as a deliberate availability choice, and its known cost** (dotted version vectors literature, Preguiça et al., arXiv:1011.5808; Antidote SQL, arXiv:1902.03576; semantic-conflict work, arXiv:2602.19231). [verified this run — titles and abstract-level snippets only; **none read in full**] — The counter-case to any proposal that C2A2 adopt strict serialisation. "The Last Write Wins (LWW) strategy resolves conflicting writes by accepting the most recent write, though this can result in lost updates and is **usually the default in several distributed systems**." LWW is chosen, not stumbled into: it buys availability and partition tolerance at a known cost in silent overwrites. A fleet of independently scheduled agents that must make progress while the human is away is exactly the workload for which LWW is the conventional default — which means the fleet's current behaviour is a recognisable design point, not an unforced error, and the argument for changing it has to be made on the value of the specific writes being lost.
3. **Structured handover evidence — AHRQ *Making Healthcare Safer IV*, "Use of Structured Handoff Protocols for Intrahospital Within-Unit Transitions"** (NCBI Bookshelf NBK613742; AHRQ rapid-research report). [verified this run — snippet level via the AHRQ/NCBI summary; **not read in full**] — The challenge to the queue's clinical-handover analogy at its own strength. "**SBAR** ... provided **low-certainty** evidence that it can improve patient safety clinical outcomes, while **I-PASS** provided **moderate-certainty** evidence." 4. **I-PASS implementation outcome studies** (orthopaedic surgery I-PASS intervention, PMC9447790; tertiary paediatric implementation, PMC10014024). [verified this run — snippet level] — The concrete form of the same caution. "Notable improvement was observed in 8 of 9 targeted quality elements and adherence ... was sustained at markedly improved levels," yet "**no statistically significant differences were observed** between rates of 30-day readmission, 90-day readmission, urinary tract infection, pulmonary embolism/deep vein thrombosis, surgical site infection, or delirium before and after the intervention." Process measures moved; outcome measures did not. ### Strength of challenge: Moderate

### Summary

The events are as described, but the item's reading of them is contestable at its centre. The second run did not discharge an escalation to avoid work; it *fixed the defect the escalation was about* — "all three rewrote on both frames," with the specific corruptions named (Day 63's invented eighth article, Day 65's erased Q.9 a.5). In every framework I searched, escalation is a request for a decision rather than a lock on an artefact, and the fleet should be slow to make it one: an escalation-as-lock, in a system whose human has now been absent eleven days, converts every handed-up defect into a defect that cannot be repaired until he returns. That cost is not hypothetical here — it is the same eleven-day window that ASSUMPTION-1077 is trying to reason about. The queue's proposed literature is also weaker than its reputation: AHRQ's synthesis grades SBAR at *low* certainty and I-PASS at *moderate* certainty for clinical outcomes, and the implementation studies show handoff quality improving with outcomes unchanged. Adopting a handover protocol is a process intervention with process-level evidence, and it would not have prevented this. The more exact diagnosis is mechanical: two runs performed a read-modify-write on shared review state with no version check, which is a lost-update anomaly, and the standard remedy is a version field that makes the second write fail rather than a rule about who may write. Last-writer-wins, meanwhile, is the deliberate default in most distributed systems precisely because it preserves availability — so the fleet's present behaviour is a recognisable design point whose cost has to be argued write by write. What none of this touches, and what is the item's durable contribution, is that **Tom is now holding an escalation for a condition that no longer exists**, and no artefact in the fleet records that it was superseded. That is an auditability failure, not an authority failure, and it has a much cheaper fix.

### Specific risks

If the item is read as calling for escalation-as-lock, the fleet acquires an unbounded hold queue whose release depends on an absent human. On the current record — eleven dark days, "no dispositions submitted from the 08-12, 08-13, or 08-14 pages" (ASSUMPTION-1076) — that queue does not drain. Every defect handed up would then remain live in the corpus, and the fleet's throughput on real repairs would fall to whatever the human clears. The Day 63/65 corruptions would still be in the files.

If the item is read as calling for a handover protocol, the AHRQ evidence predicts the fleet's handoffs will improve on process measures and the double-disposition rate will not necessarily move. Effort spent there is effort not spent on the version check that would have stopped this instance mechanically.

If the item is dismissed, the live hazard is the stale escalation: the human returns to a queue containing at least one item — probably three — that were resolved hours after being raised, and no field distinguishes them from open ones. The predictable consequence is that his first attended session is spent re-adjudicating closed matters, which is exactly the confound ASSUMPTION-1077 warns will contaminate the override-rate measurement.

A second-order risk specific to this fleet: ASSUMPTION-1071 records an independent double-disposition on Days 013/044/055 the same day. Two instances in one day is not an anomaly, it is a rate, and the rate is what should be measured before any remedy is chosen.

### Mitigations available

(a) **Version the review state.** A monotonically increasing version or last-modified token on each day's `needs_review` record, checked at write time. The second run's write fails, it re-reads, and it then either defers or supersedes with the prior disposition in hand. This is one field and it would have caught both this instance and ASSUMPTION-1071's.
(b) **Give escalations a lifecycle, not a lock.** `RAISED → SEEN → SUPERSEDED-BY-<run> → WITHDRAWN/DECIDED`, with supersession permitted but *recorded*. This preserves the fleet's ability to fix things while the human is away and closes the auditability gap — which is the defect this file argues is actually load-bearing. It also directly protects the ASSUMPTION-1077 measurement, since a superseded item can be excluded from the override denominator instead of silently inflating it.
(c) **Require read-before-write of the escalation register.** The cheapest possible version of (a): before disposing of any day, read the open-escalation list for that day. "Neither run references the other" is a read failure before it is an authority failure.
(d) **Measure the rate before designing the protocol.** Two same-day double-dispositions (this item and ASSUMPTION-1071) is a datum, not a trend. Count double-dispositions per week over the existing transcripts; the number decides whether a protocol is worth its cost or whether (a) and (c) suffice.
(e) **If a protocol is adopted anyway, take the AHRQ caution with it:** instrument the *outcome* (double-disposition rate, stale-escalation count), not the *process* (protocol adherence), because the literature's clearest finding is that these two come apart.

## STEELMAN

**Item:** ASSUMPTION-1070

**Strongest counterargument:** Look at what the second run actually did. It took three files that a prior run had declined to touch, found the defects were real, and repaired them — Day 63's invented eighth article, Day 65's erased Q.9 a.5, locators and article lists corrected on both frames. The corpus is better than it was. The item calls this a boundary failure because "the escalation reserved for Tom was discharged by an agent," but that phrasing smuggles in a premise: that raising an escalation places a hold on the artefact. Nothing in incident management works that way, and there is a good reason it does not. An escalation is a request for a decision; if it were also a freeze, then in a system whose human has been absent for eleven days and has submitted no dispositions since 08-12, every escalated defect would be a defect that cannot be fixed. The fleet would have converted its human's absence from an oversight gap into a repair embargo. That is a worse system, not a safer one, and it fails in the direction the fleet cannot see. The proposed literature does not rescue the framing either: AHRQ grades SBAR at low certainty and I-PASS at moderate certainty for clinical outcomes, and the implementation studies are consistent — adherence up, outcomes flat. A handover protocol would have made these two runs hand off beautifully to nobody, since neither knew the other existed. Which is the real point. This is not an authority failure at all; it is a read-modify-write on shared state by two uncoordinated writers, and it has a boring, mechanical, well-understood fix — a version field, so the second write fails and the second run learns what it needs to know. Last-writer-wins is the default in most distributed systems by deliberate choice, for availability; the fleet inherited that default, and the argument for changing it is an argument about specific writes, not about who is allowed to hold a pen. The one thing that genuinely is broken, and that neither the authority framing nor the protocol framing addresses, is that Tom is right now holding an escalation for a defect that was fixed hours after he was asked about it, and there is no field anywhere in this architecture that could tell him so.

**What would need to be true for C2A2 to be safe:** Escalations must be *observable* — with a recorded state that includes supersession — and shared review state must be *versioned*, so that a second writer discovers the first rather than overwriting it. Given both, agent supersession of an escalation is safe and desirable, because it is visible and reversible. Given neither, the hazard is not that agents act on escalated matters; it is that no one, human or agent, can determine what is still open. If the fleet responds by prohibiting agent action instead, it will be safe from this specific pattern and exposed to a larger one: an unbounded hold queue gated on an absent reader.

**How to test:** **One:** count double-dispositions across the existing transcript corpus — same artefact, two dispositions, same day, no cross-reference. This item and ASSUMPTION-1071 give two in one day; the corpus will say whether that is the rate. Needs no attendance. **Two:** check whether the three escalated days are still present in Tom's escalation queue with no supersession marker. If they are, the stale-escalation defect is confirmed by inspection and it is the highest-value single fix in this file. **Three, and it is the discriminating experiment:** ask whether the second run's repair was *correct*. If the rewrites are right, the item's framing loses most of its force and the remedy is observability; if the rewrites introduced errors of their own, the authority framing gains substantially and the case for a hold becomes real. The item asserts the boundary was crossed but does not assess whether crossing it produced a worse corpus, and that is the fact on which the whole disagreement turns.
