SEARCH-AGAINST-PRESUMPTION-855:
  Date searched: 2026-08-24
  Original item: PRESUMPTION-855
  Original statement: A registry's last-run field is presumed to record whether a task ran, so its absence is read as non-firing.

  Reading challenged: The presumption itself — that a completion-time field is a record of execution. The distributed-systems literature treats this exact inference as a named error. A last-run field records *successful completion*, not *attempted execution*, and the gap between those two is where "started and died", "started and hung", and "started, ran, produced nothing" all live indistinguishably. The literature does not merely note this; it prescribes a specific structural remedy (a start record, a lease, or a heartbeat) and treats the remedy as a precondition for the monitor being sound at all. The inverse challenge — that completion-only logging is sometimes correct — holds, but only under a commit-semantics reading that C2A2 is not using.

    7. **Inverse challenge — where completion-only logging is correct.** Kafka consumer offset semantics [Confluent documentation and consistent practitioner material — VERIFIED as a documented standard]. — Committing the offset *before* processing yields at-most-once (possible loss); committing *after* processing yields at-least-once (possible duplicates); the fundamental rule for at-least-once is "commit only after the side effect completes". Challenge to the challenge: there is a large and correct family of systems in which the completion record is deliberately the only durable record, because its job is to prevent double-execution rather than to prove execution.   Strength of challenge: Strong

  Summary: The presumption is not merely wrong; it is known-wrong, in the specific sense the crux asked about. The inference "no last-run entry, therefore did not fire" asserts a distinction that Chandra and Toueg showed is unavailable in an asynchronous system from silence alone, and the modern operational literature — gray failure and differential observability — identifies the resulting blind spot as the leading cause of availability breakdowns rather than a corner case. The prescribed remedies are established and cheap: a start checkpoint written before the work (documented by AWS as the basic unit of its durable-execution model), a lease with a TTL plus a reaper, or the two-ping heartbeat form that operations vendors recommend for exactly this reason and describe in exactly these terms — so that you can see "whether it was running, failed, or missed entirely". The inverse holds in a real and important class of systems: write-ahead logs and at-least-once message consumers deliberately record only completion, because the record's purpose is idempotency, not liveness. But those systems read an absent record as *unknown, re-run it*, never as *did not happen*. C2A2 has taken the completion-only logging discipline and paired it with the negative-inference reading that only a provably complete record would license. That is the combination the forensic literature specifically refuses, and the one the distributed-systems literature designs around.

  Specific risks:
    - Silent non-execution is indistinguishable from silent mid-run death. Every diagnosis built on the empty field is a coin-flip between "scheduler never fired" and "agent fired, crashed, and left nothing", and these have opposite remedies (fix the scheduler vs. fix the agent).
    - Wrong-remedy expenditure: if the true fault is a crashing agent, effort spent on scheduler configuration is wasted and the crash continues, producing more empty fields that are read as more scheduler failure. This is self-reinforcing.
    - Partial-run contamination: a task that started, wrote artefacts, and died before completion leaves those artefacts in the estate with no last-run entry claiming them. They are orphaned but not marked orphaned, and they will be read later as products of some other run.
    - Gray-failure invisibility: a task that fires, runs to completion, and produces degraded or empty output writes a *successful* last-run entry. The registry therefore reports health at exactly the point where PRESUMPTION-860's concern (zero yield) becomes live, and the two blind spots compose.
    - Retry hazard: with no lease or claim record, a supervisor that re-fires an apparently-unfired task can produce concurrent duplicate execution over the same corpus, which — given the shared-corpus correlation identified in PRESUMPTION-859 — would then be read as agreement between two runs.
    - The negative inference is load-bearing for scheduling decisions across the estate, and it has no confidence interval attached anywhere.

  Mitigations available:
    - Write a start record before the work, not after. This is the single change that converts the registry from a two-state instrument (completed / silent) into a three-state one (never started / started and unfinished / completed), and it is what the located vendor and operations material uniformly prescribes.
    - Give the start record a lease with an expiry, and add a reaper that transitions expired leases to a distinct TIMED-OUT state rather than leaving them silent. An expired lease is a positive record of "started and died" — the state the registry currently cannot express.
    - Change the *semantics of absence* in the reading code from "did not fire" to "unknown". Where the current inference is load-bearing, require corroboration from an independent channel (filesystem mtimes, artefact counts, process logs) before acting on it. Note that this corroboration must be genuinely independent — the shared-channel problem in PRESUMPTION-859 applies here directly.
    - Emit an explicit failure ping on abnormal exit, so that the common case of a caught-and-logged crash is distinguishable from the uncommon case of a hard kill.
    - Record a heartbeat during long runs, not just at boundaries, so that "hung" is distinguishable from "still working".
    - Audit the estate for decisions already taken on the strength of an empty last-run field, and re-open any whose remedy was directed at the scheduler.

  STEELMAN:
    Item: PRESUMPTION-855
    Strongest counterargument: The registry field records completion, and completion is a strictly weaker fact than execution — so reading its absence as non-execution is not a conservative approximation but a logical error, and the error is one the field has already named, formalised, and solved. Chandra and Toueg proved that silence cannot distinguish a dead process from a slow one; the gray-failure literature then showed that in practice the systems most likely to fail are precisely the ones that fail without producing a fail-stop signal, so a detector calibrated on silence is blindest exactly where the risk concentrates. The remedy is not sophisticated: write something before you start. AWS documents a START checkpoint as the basic unit of durable execution; scheduler practice pairs a lease TTL with a reaper so that an expired claim becomes a positive record of "started and died"; and operations vendors recommend a start ping alongside the completion ping in one sentence that names the exact three states C2A2 cannot tell apart — running, failed, missed entirely. Against this, the only serious defence of completion-only logging comes from write-ahead logs and at-least-once consumers, where the commit record is deliberately the sole durable artefact — but those systems read an absent record as *unknown, replay it*, never as *did not occur*. C2A2 has adopted the weaker record and the stronger reading simultaneously, which is the one pairing no established design endorses, and it did so without noticing, which is what makes this a presumption rather than a tradeoff.
    What would need to be true for C2A2 to be safe: (a) The write of the last-run field would have to be atomic with the *decision to run*, not with the completion of the run — otherwise the field cannot carry the fact the reader wants; (b) the execution environment would have to be genuinely fail-stop, so that a crashed run is guaranteed to leave no partial artefacts and no ambiguity — which is false for any agent that writes incrementally; (c) the registry write would have to be reliable and durable, so that a lost write is not confusable with a non-run; (d) either no downstream decision would depend on the fired/not-fired distinction, or every such decision would have to carry an independent corroborating channel; and (e) that corroborating channel would have to be independent in fact and not merely in name (cf. PRESUMPTION-859), which rules out any check that reads the same registry.
    How to test: Three tests, all cheap and all decisive. (1) Injection test: kill a scheduled agent mid-run and observe what the registry shows. If the resulting state is indistinguishable from a run that never fired, the presumption is falsified by construction and no further evidence is needed. (2) Reconciliation audit: for the last ninety days, cross-reference empty last-run fields against filesystem artefact mtimes, process logs, and output directories. Every case where artefacts exist under an empty field is a confirmed instance of the presumption failing, and the count is the current error rate of the inference. (3) Decision trace: enumerate the decisions taken in the estate whose premise was an empty last-run field, and classify each by whether the remedy chosen would have been correct under the alternative reading ("started and died"). The proportion that would have been wrong is the accumulated cost of the presumption, and — given the self-reinforcing dynamic noted in the risks — it should be expected to be rising rather than flat.
