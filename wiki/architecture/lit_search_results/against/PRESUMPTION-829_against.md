  Sources:
    1. Alpern, B. & Schneider, F.B. 1985. "Defining Liveness." Information Processing Letters 21(4):181–185. — Establishes the safety/liveness decomposition. The property "this run produced output" is a liveness property ("something good eventually happens"), and the follow-on runtime-verification literature (e.g. "Refining the Safety–Liveness Classification of Temporal Properties According to Monitorability," Springer 2019) shows that many commonly used liveness properties are *not monitorable*: no finite prefix of the execution establishes a verdict. This challenges the item's implied remedy — there is no general instrument that can, from a finite observation, distinguish "produced nothing yet" from "will never produce anything."
    2. Chandra, T.D. & Toueg, S. 1996. "Unreliable Failure Detectors for Reliable Distributed Systems." Journal of the ACM 43(2):225–267. DOI 10.1145/226643.226647. — Failure detectors in asynchronous systems are necessarily unreliable: they may suspect correct processes and may fail to suspect crashed ones. A "did this run actually do work" detector inherits the same completeness/accuracy trade-off, so any mute-run instrument C2A2 builds will itself have a false-positive and false-negative rate that must be budgeted, not assumed away.
    3. Fischer, M.J., Lynch, N.A., Paterson, M.S. 1985. "Impossibility of Distributed Consensus with One Faulty Process." Journal of the ACM 32(2):374–382. — The underlying impossibility: in an asynchronous system a slow process and a crashed process are indistinguishable. Directly limits how strong a guarantee any "fired ⇒ ran" instrument can offer; the seven mute runs may be indistinguishable, at observation time, from seven slow ones.
    4. Parasuraman, R. & Riley, V. 1997. "Humans and Automation: Use, Misuse, Disuse, Abuse." Human Factors 39(2):230–253. — Documents "disuse": neglect and disabling of automation caused by alarms that activate falsely. A mute-run detector with the false-positive rate that Chandra & Toueg's result guarantees is exactly the kind of aid that gets ignored, so the instrument can be present and non-functional as a control.
    5. Parasuraman, R. & Manzey, D.H. 2010. "Complacency and Bias in Human Use of Automation: An Attentional Integration." Human Factors 52(3):381–410. — Complacency effects mean adding a monitoring layer redistributes attention rather than adding it; the layer that is trusted is the layer that stops being checked. Challenges the assumption that instrumenting mute runs increases detection overall.

  Strength of challenge: Moderate

  Summary: Nothing in the literature disputes that a scheduler's "OK" is an availability signal rather than an effectiveness signal — that distinction is standard and the presumption is plainly unsafe as stated. What the literature challenges is the fix the item points at. "This run produced output" is a liveness property, and the monitorability results show that a large class of liveness properties admits no verdict from any finite prefix; FLP and Chandra–Toueg give the underlying reason, that a slow process and a dead one are indistinguishable in an asynchronous system. So the instrument C2A2 wants cannot be built to give a guarantee; it can only be built as an unreliable detector with a tunable trade-off between missing mute runs and falsely flagging slow ones. The human-factors evidence then says that whichever way that dial is set, the detector's own reliability determines whether it is used at all: too many false alarms and it is disused, too few and it induces complacency in the layers above it. The presumption is real; the remedy is a rate-tuning problem, not a coverage problem.

  Specific risks: If C2A2 builds a mute-run instrument and treats its silence as proof that all runs produced work, it has moved the presumption one layer up rather than removing it — the new register now carries the same unwarranted finality. If the grace window is set to the nominal cadence, legitimately slow runs will be flagged as mute, and the false-alarm rate will drive disuse of the alarm, at which point genuine mute runs pass unremarked with an audit trail suggesting they were checked. If "produced nothing" is defined as "wrote no output file," legitimate no-op runs (nothing to do that cycle) become indistinguishable from failures, and the mute count becomes noise. Conversely, a definition tuned to suppress no-ops will suppress the failure class it was built for. The measured "seven of twenty-nine" is itself computed after the fact from this pipeline's own file, so it inherits whatever definitional choice that file made, and no other register can corroborate it.

  Mitigations available: Instrument for a *safety* property rather than a liveness one — have each run emit a positive completion record with a work-count field, so the absence of a record is a bounded, monitorable condition rather than an unbounded wait. Set grace windows from the observed runtime distribution (cadence plus variance), not from nominal cadence. Distinguish three terminal states explicitly — completed-with-work, completed-no-work-required, and did-not-complete — so no-ops do not pollute the mute count. Test the detector by deliberately killing runs and confirming it fires (the untested-switch problem). Publish the detector's own false-positive/false-negative rate alongside its output so downstream consumers can weight it. Keep the mute count in a register outside the pipeline that produces it, so it is not self-reported.

  STEELMAN:
    Item: PRESUMPTION-829
    Strongest counterargument: The presumption is correctly identified but the item frames it as a gap in instrumentation, when the formal results say it is partly a limit on what instrumentation can do. "This run produced output" is a liveness property, and Alpern–Schneider plus the monitorability literature establish that many such properties yield no verdict from any finite observation — you cannot tell, at any moment, whether a run has failed to produce output or has not produced it yet. FLP gives the sharp version: in an asynchronous system, slow and dead are indistinguishable. So the instrument C2A2 is missing is not merely unbuilt; in its strong form it is unbuildable, and what can be built is an unreliable detector whose false-alarm rate will determine whether anyone attends to it. The human-factors evidence then predicts the likely outcome of building it anyway: a noisy alarm gets disused, a quiet one gets over-trusted, and either way the number of undetected mute runs does not go to zero. The honest version of the item is "we have no bound on the mute rate," which is a weaker and more actionable claim than "no instrument reports the number."
    What would need to be true for C2A2 to be safe: (a) the property being monitored is reformulated as a safety property — a positive completion record whose absence within a bounded, distribution-derived window is the alarm condition; (b) the three terminal states (work done / nothing to do / did not complete) are distinguished at source, so the mute count is not definition-dependent; (c) the detector's own error rates are measured by fault injection and published, so downstream users do not treat its silence as proof; (d) the mute count is recorded outside the pipeline that generates it, so it is independently corroborable; (e) grace windows come from observed runtime variance rather than nominal cadence.
    How to test: Fault injection. Over a controlled window, kill a known number of scheduled runs at a known point (before any output, after partial output, and after completion but before the record is written) and count how many the detector reports. That yields the completeness rate. Then run an equal number of deliberately slowed-but-correct runs and count false alarms — that yields the accuracy rate. Report both. Separately, re-derive today's "seven of twenty-nine" from a register other than the pipeline's own file; if no such register can produce the number, that fact is itself the finding, and it is stronger stated as "unmeasurable from independent evidence" than as "seven."
