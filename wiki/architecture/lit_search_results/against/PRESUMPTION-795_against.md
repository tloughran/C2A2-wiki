### Strength of challenge: Moderate

### Summary

The observation is solid and the pattern is real, but the residual claim attributes the failure to the wrong variable. Narrative disclosure demonstrably can be durable at scale: the NTSB has issued more than 12,480 prose recommendations with an acceptance rate above 82%, and the mechanism is not a structured schema but a named addressee carrying a response obligation — and the GAO's finding that 35% of decade-old aviation recommendations remain unimplemented pins down exactly which part is load-bearing, since acceptance without an action deadline decays. The software-specific evidence points the same way: the ADR action-research study found that *where documentation is stored* has a massive influence on its usefulness, which recasts C2A2's four substitutions as off-the-read-path rather than as insufficiently structured. The literature 14b names as its basis fits less well than it appears to: Tucker and Edmondson's mechanism is that front-line workers patch and *say nothing*, and C2A2's runs did say something, which places the fleet on the second-order side of their distinction rather than the first. And the implied remedy inherits the disease — the control-effectiveness literature's standard failure list (approvals after the fact, controls that exist but are inconsistently applied, static records of obligation) is a description of registers, so relocating a substitution into a register without a scheduled reader reproduces the same non-durability with better provenance. The strongest surviving version of the item is not about prose at all: it is that a declaration with no addressee and no scheduled read is not a transmission, in any medium.

### Specific risks

If the medium attribution is adopted, the fleet will build a register, route substitutions into it, and observe no change — because the four substitutions failed for want of a reader, and the register will have the same number of scheduled readers as the prose did, namely zero. Worse, the register will then be cited as evidence that the control exists, which is the PREMISE-110 configuration: a documented control that is not performed. The specific cost is one build cycle plus a durable false assurance.

If the challenge is over-weighted and the item is dismissed, the concrete hazard is unchanged and is the item's best evidence: a verifier making and declaring the same substitution on three consecutive nights is an unbounded loop, and the cost of that loop compounds nightly. Three nights is already enough to establish that the current path does not terminate.

There is also a specificity risk the item should not lose: the four substitutions were *method* substitutions. The scoping-review finding that fewer than 7% of incident recommendations are strong controls suggests the more consequential question is whether the substituted methods are equivalent to the specified ones — a substitution silently weakening a check is a defect whether or not it is durable.

### Mitigations available

(a) **Give every declaration an addressee and a due date** — the NTSB's actual mechanism, and cheap. A substitution declared without a named recipient obliged to respond is not a transmission. (b) **Fix the read path, not the format.** Establish whether the artefact a subsequent run of the same task loads includes the location where substitutions are written; if not, that is the whole defect and it is one path change. The ADR finding says storage location dominates. (c) **Bound the loop explicitly**: a substitution declared N times by the same task without the underlying task file changing should escalate on a counter, not repeat. Three consecutive nights is already an actionable trigger and requires no register. (d) **Grade substitutions by control strength**, not just record them, so that a substitution that weakens a check is distinguishable from one that is equivalent. (e) Before building any register, state what will read it and on what schedule; if that sentence cannot be written, the register will fail exactly as the prose did.

### Recommendation: PARTIALLY-CHALLENGED

## STEELMAN

**Item:** PRESUMPTION-795

**Strongest counterargument:** Prose is not the problem, and the evidence that it is not is very large. The NTSB has issued over 12,480 narrative recommendations since 1967 with an acceptance rate above 82% — no schema, no structured register, just prose addressed to a named recipient who is legally obliged to respond within 90 days. The GAO's complementary finding, that 35% of aviation recommendations open more than a decade remain unimplemented for want of any statutory *action* deadline, identifies precisely which variable carries the durability: addressee plus obligation, not format. Software's own evidence agrees — the ADR action-research study found that where documentation is stored has a massive influence on whether it is useful, which means C2A2's four substitutions failed because they were off the read path of the next run of that task, not because they were sentences. And the literature the item leans on cuts the other way on inspection: Tucker and Edmondson's finding is that front-line workers patch problems and *do not report them*, so a fleet whose runs declare their substitutions is already past the failure they documented. Worst of all for the implied remedy, the control-effectiveness literature's standard failure list — approvals after the fact, controls that exist but are inconsistently applied, checklists that function as static records of obligation rather than systems of execution — is a description of registers. Build the register and you will have moved four undurable declarations into a place with the same zero scheduled readers, and acquired a documented control you are not performing. The real finding here is much cheaper and much sharper than the item states: a verifier that declares the same substitution three nights running is an unbounded loop with no escalation counter, and that is fixable tonight without any new artefact at all.

**What would need to be true for C2A2 to be safe:** Every declared substitution must have (i) a named addressee — a task, not a document — that is obliged to act, (ii) a due date or an escalation counter, and (iii) a location provably on the read path of the next run of the affected task. Given all three, prose is sufficient and the medium question is moot. Given none — the current state — the item's hazard is entirely real, but a register supplies only a location, not the addressee or the obligation, and so would fix at most one of the three.

**How to test:** Direct and cheap. Take the file or field into which a substitution declaration is currently written and check whether it is loaded by the next scheduled run of the same task. If it is not, the defect is the read path and the medium hypothesis is refuted outright. Second test: instrument the addressee mechanism on a single case — attach the verifier's three-times-repeated substitution to a named recipient with a due date, and see whether it lands within one cycle. If it does, the NTSB mechanism transfers and no register is needed. Third, and it settles the strength question the item does not ask: audit the four substituted methods against the specified ones and record whether any of them weakens a check. Durability of a substitution that should not have happened is not an improvement.
