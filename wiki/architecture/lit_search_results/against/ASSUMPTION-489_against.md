  Sources:
    1. Pixee, "SAST False Positives: 91% Are Noise" and Corgea, "How to reduce False Positives in SAST" (retrieved 2026-07-21). Real-world SAST false-positive proportions run to 76% and above 90% once all discarded cases are counted. An 11-of-13 (85%) false-positive rate is squarely within the normal range for rule-based detectors, so the finding is unremarkable as a rate — which challenges the framing of this as an exceptional defect while fully supporting the underlying concern.
    2. Snyk, "Minimizing False Positives"; OX Security, "Why False Positives Are the Bane of Application Security Testing" (retrieved 2026-07-21). Reducing false positives by loosening detection thresholds or disabling policies "carries the risk of suppressing detection rather than improving it," and a high false-positive rate converts into a false-NEGATIVE outcome as true positives get dismissed. This is the direct challenge to the remedy: the proposed fix (tighten the locus regex, re-run, diff) moves the detector along the precision/recall frontier, and the item treats a resulting drop to zero as confirmation rather than as a signal requiring its own check.
    3. Enterprise static-analysis design norms as summarised in "Reducing False Positives in Static Bug Detection with LLMs: An Empirical Study in Industry," arXiv:2601.18844 (retrieved 2026-07-21). Enterprise analysers deliberately prioritise recall over precision so that no potential bug is missed, accepting high false-positive rates as the cost. A detector designed this way is not defective for producing 85% false positives; it is operating as specified, and "0 genuine" after tightening may mean the tool has been retuned away from its design point.
    4. Vectra AI, "Alert fatigue: causes, real cost, and how to fix it" (retrieved 2026-07-21). Desensitisation raises the likelihood that genuine findings are overlooked; teams that have investigated many false alerts stop applying the same rigour to new ones. Supports the item's motivation.
    5. Regression-testing practice (Wikipedia, "Regression testing"; Repeato, "Re-Running Regression Tests After Bug Fixes"; retrieved 2026-07-21). Verification that a fix has not introduced new defects requires an independent oracle — a known-good and known-bad corpus — not merely a re-run showing fewer findings.

  Strength of challenge: Moderate
  Summary: The claim is credible and its rate is ordinary: 85% false positives sits inside the documented range for rule-based detectors, and enterprise analysers are deliberately built that way, trading precision for recall. So "the detector had a real bug" and "the detector was working as designed for a recall-first tool" are both consistent with the evidence, and the item does not distinguish them. The sharper challenge is to the remedy and to the "0 genuine" conclusion. The security literature is explicit that reducing false positives by tightening thresholds risks suppressing detection rather than improving it, and the item's proposed validation — tighten, re-run, diff — has no oracle: a detector that now reports nothing is indistinguishable from a detector that now detects nothing. Reaching zero is the outcome most consistent with a correct fix AND most consistent with an over-tightened one, and nothing in the proposed procedure tells them apart. The parallel to the false-negative conversion described in the alert-fatigue sources is exact.
  Specific risks: The locus regex is tightened, the re-run reports zero, the detector is marked healthy, and genuine metaphysical guardrail violations pass unflagged indefinitely — a silent detector is worse than a noisy one because it produces no signal to investigate. Second risk: "0 genuine" is quoted downstream as evidence that the guardrail is not being violated, when it is only evidence about the detector. Third risk: the same defect class is present in sibling detectors and the audit is scoped only to this one.
  Mitigations available: Build a labelled corpus before re-running — a handful of known-genuine violations (synthesised if necessary) and known-clean passages — so that the post-fix run has an oracle and recall is measurable rather than assumed. Report precision and recall separately rather than a violation count. Treat "0 findings" as a condition requiring positive proof of liveness, exactly as a fail-safe trigger requires proof-testing. Carry out the item's second recommendation (audit remaining detectors for the same defect class), which is the highest-value part of the item and is independent of the precision/recall question.

  STEELMAN:
    Item: ASSUMPTION-489
    Strongest counterargument: The finding is sound and the fix is where the danger is. An 85% false-positive rate is not evidence of an exceptional defect — real-world static-analysis tools run at 76% to over 90%, and enterprise analysers are deliberately tuned recall-first on the reasoning that a missed defect costs more than a wasted investigation. So the detector may have been behaving close to its design point, and the "real parser bug" reading, while plausible, is not the only one available. What follows is riskier. The remedy is to tighten the locus regex and re-run, and the security literature states directly that reducing false positives by loosening or narrowing detection risks suppressing detection rather than improving it, converting a false-positive problem into a false-negative one. The item then treats a resulting count of zero as the confirming result — but zero is exactly what an over-tightened detector produces, and the proposed diff has no oracle capable of distinguishing the two. This is the same structure as PRESUMPTION-511's point about reproduction, arriving from the detector side: a re-run that agrees with itself confirms nothing about correctness. A silent guardrail detector in a system that quotes its output downstream is a worse failure than the noisy one it replaced, and it will not announce itself.
    What would need to be true for C2A2 to be safe: That a labelled corpus with known-genuine violations exists before the tightened detector is trusted, so that recall is measured rather than inferred from a lower count.
    How to test: Construct or synthesise five passages that genuinely violate the metaphysical guardrail and five that clearly do not. Run the tightened detector over all ten. If it flags fewer than five of the true violations, the fix has traded recall for precision and "0 genuine" in production means nothing. Then apply the same positive control to every sibling detector before auditing them for the defect class.
