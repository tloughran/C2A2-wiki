  Strength of challenge: Strong

  Summary: The presumption is contradicted in both domains where the question has been measured. In software engineering, corrections are a leading source of defects rather than a low-risk direction: review-reported figures put fix-induced bugs at 29% for one corpus of fixes, 12.2% of pull requests under full CI and review, and regressions at roughly half of all reported bugs in the Linux kernel and 51% in Chromium. Whatever the precision of individual figures — and these come to this file through a secondary review, which is a real limitation — the magnitude is not in dispute, and "regression error repair" exists as its own research programme with its own benchmarks, which would be unnecessary if corrections were safe. In the scholarly record, the analogue is sharper still: formal retraction, the most heavily governed correction mechanism available anywhere, still produces retractions that are flawed procedurally and on the merits, with no reliable route to reversing one — the precise structural gap the item identifies in C2A2's lifecycle, reproduced in a setting with vastly more oversight. And even correct retractions propagate inconsistently and incompletely, so the corrective direction carries a second failure mode the lifecycle also cannot represent. Finally, the base-rate framing matters: publishing tolerates a nonzero retraction error rate because retractions are rare, about five per 10,000 articles. C2A2 corrects at a far higher rate, so the same per-correction error probability yields a far larger absolute harm.

  Specific risks:
    - Correction-induced regression as the dominant defect source: if the software base rates transfer even approximately, corrections are the largest single source of new defects, not the smallest.
    - No terminal state for a wrong correction: the item's own observation. This is worse than the flag case (PRESUMPTION-833), because a wrong correction actively reverses work that was right, whereas a wrong flag merely costs an investigation.
    - Amplification through the correct-repairs channel: the near-miss recorded in ASSUMPTION-1153 — a retraction that would have licensed reversing correct Day 268/269 repairs — is this presumption's concrete instantiation, and it was caught by an ad hoc grep rather than by a gate.
    - Propagation failure of correct corrections: a correction that is right but does not reach every artefact leaves the record internally inconsistent, and no state exists to detect the inconsistency.
    - Rate mismatch with the tolerable-error argument: the analogy to scholarly retraction only reassures if corrections are rare. They are not.
    - Compounding with PRESUMPTION-841: if a reversed correction is not distinguishable from a correction never attempted, the register cannot even count how often this happens.

  Mitigations available:
    - Gate the corrective direction at least as strictly as the detective direction, and require independent confirmation before any action that reverses prior work. The near-miss in ASSUMPTION-1153 is a worked example of what this gate would have caught.
    - Add lifecycle states for a withdrawn correction and for a correction that failed to propagate, and make both terminal and machine-readable. The retraction literature shows that absence of the second state is a real and separate failure.
    - Apply change-impact analysis before corrections: the review-reported causes of fix-induced regression are insufficient test coverage, poor change impact analysis, high coupling, and cognitive overload — three of the four are addressable by requiring a stated blast radius before a correction is applied.
    - Measure C2A2's own correction-error rate rather than importing one. Count corrections issued and corrections subsequently reversed; that ratio is the local analogue of the 12.2%–29% figures and is computable from existing records.
    - Make corrections reversible by construction: never destroy the prior state, so that a wrong correction is undoable rather than merely regrettable.
    - Verify the review-reported figures against their primary sources before any of them is quoted in a C2A2 artefact as established.

  STEELMAN:
    Item: PRESUMPTION-842
    Strongest counterargument: The corrective direction is where the defects come from. In two major codebases, regressions constitute roughly half of all reported bugs, and changes introduced under full linting, unit testing, regression testing and code review still carry a measured defect-introduction rate in the low double digits — a figure the reporting explicitly calls conservative because undetected and unlinked defects are excluded. There is a research programme devoted to repairing regression errors, which would be superfluous if fixing things were the safe direction. The scholarly-record analogue closes the argument: retraction is the most heavily governed correction mechanism in existence, with editors, committees and appeals, and it still produces retractions that are procedurally and substantively wrong, with no reliable mechanism for undoing one — which is exactly the missing lifecycle state the item identifies, reproduced in a domain with orders of magnitude more oversight than C2A2 has. Even correct retractions propagate incompletely, so the corrective direction has two failure modes and C2A2's lifecycle can represent neither. And the reassurance that corrections are rare enough for a small error rate to be tolerable does not transfer: publishing retracts about five papers per ten thousand, while C2A2 corrects constantly, so the same per-correction risk produces a much larger absolute harm. The item's own near-miss — a retraction that would have licensed reversing correct repairs, stopped by one grep — is not an anecdote but the predicted case.
    What would need to be true for C2A2 to be safe: (a) C2A2's own correction-error rate would have to be measured and shown to be materially below the software base rates, rather than assumed; (b) corrections would have to be non-destructive, so that a wrong one is reversible rather than terminal; (c) the lifecycle would have to carry terminal states both for a withdrawn correction and for a correction that failed to propagate; (d) the corrective path would have to require independent confirmation, since the one case that was caught was caught by an unplanned check; (e) the specific figures relied on here would have to be traced to their primary sources — they currently come through a single secondary review, which is this file's weakest link and should be stated as such wherever it is cited.
    How to test: Compute the local rate. Over the past sixty days, count corrections issued and count corrections subsequently reversed or found wrong; the ratio is C2A2's own fix-induced-error rate and it is directly comparable to the 12.2%–29% range without importing anything. Then test the gate's absence: take the three candidate wrong corrections from tonight and trace, for each, what would have stopped it — if the answer in every case is an ad hoc check by a later run rather than a structural gate, the presumption is operating unopposed and the count of near-misses is a lower bound. Finally, test propagation: pick a correction known to be right and audit every artefact that referenced the corrected item; the fraction not updated is C2A2's propagation-failure rate, which the retraction literature predicts is well above zero and which no current state can detect.
