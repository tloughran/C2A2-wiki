### Strength of challenge: Weak (on the core) / Moderate (on the framing and the grade)

### Summary

The item's central proposition survives the disconfirmatory search intact, and I record that as the primary result: `[Request interrupted by user]` is **documented in the vendor's public issue tracker as appearing without any user action**, reported independently enough to be labelled a duplicate, with no correlation to command, network, load or time of day. 14b is right, and right on external evidence rather than on inference. Two things are nevertheless wrong with the item as filed. First, the **evidence 14b offers does not discriminate**: "no transcript contains a single typed human message" is a *constant* across a fleet of scheduled tasks, not a variable — under the hypothesis that a human genuinely interrupted via some non-transcript channel, and under the hypothesis that the runtime emitted the marker spontaneously, you observe exactly the same thing, so the observation carries no likelihood ratio. The discriminating comparison 14b needed and did not make is between runs that *do* and *do not* end at the marker, or between the marker's appearance and an independent host/session-lifetime record. Second, and more consequentially, this question is **already held open in the register by name**: PREMISE-141's load-bearing scope limit states that the cause of this exact marker "IS UNDETERMINED" and that the premise "licenses no claim that the interruptions were faults rather than deliberate human stops." That was validated on 2026-08-05 from four transcripts terminating at the same marker, and 15c *deliberately excluded* the interrupt-cause question. PRESUMPTION-808 is therefore a rediscovery of a known-open question presented as a new Critical finding, and the general form of its diagnosis — attribute to the actor rather than to the system — is itself already validated at PREMISE-146 clause (3). Finally, the Critical grade rests on a claim about the **35.5% base rate being computed over the same misattribution**, which does not follow: the base rate counts runs that produced no deliverable, and a run that stops at this marker produced no deliverable **whichever agent stopped it**. The attribution question changes the *cause* attributed to those failures; it does not change the *count*.

### Specific risks (of accepting the item as filed)

1. **Re-minting a held premise.** PREMISE-138 clause (1) bars in-channel repetition with no effector as a remedy, and PREMISE-135 bars terminality purchased by accumulating instances. Promoting 808 as a new Critical item duplicates PREMISE-141's scope limit and inflates the register — the exact failure the register's own duplication-check discipline (PREMISE-105) exists to prevent. The correct disposition is almost certainly **route to PREMISE-141 as an enforcement/measurement gap**, not mint.
2. **The verification-delay cost (cry-wolf in reverse).** If the marker is reclassified as untrustworthy without a replacement discriminator, every mute run acquires an open cause question with **no artefact that could close it**. The alarm literature's measured consequence of perceived unreliability is that operators verify before acting; here the verification has no terminating evidence, so the cost is unbounded and the finding is not.
3. **Over-correction into the mirror error.** 808 is written in the direction "machine failure misattributed to a human." Adopted uncritically, it licenses the opposite standing bias — every stop read as machine fault — which is the same non-discriminating inference with the sign flipped. PREMISE-141's symmetric wording ("both clauses hold either way") is the guard, and it is the guard 808 as filed does not carry.
4. **Grade inflation displacing real Criticals.** A Critical grade on a question that (a) is already registered as open, (b) has a named cheap remedy in ALCOA+-style attributable logging, and (c) does not change the failure *count*, competes for the same finite closure capacity that PRESUMPTION-812 says is the fleet's binding constraint. This is a live coupling between two items in the same batch.

### Risk of dismissing the item — recorded at full strength

The item is substantively correct and the correction is cheap. Nothing above should be read as a reason to leave the marker unqualified. Concretely: the vendor issue tracker holds independent reports of spontaneous emission; the SDK issue (#366) indicates at least one code path where a programmatic interrupt surfaces as an error rather than a clean cancellation; and the fleet currently has **no field anywhere** in which "the runtime stopped this" is a representable answer — which is PREMISE-146's attribution-field defect reappearing in the terminal-state record.

### Mitigations available

(a) **Route to PREMISE-141, do not mint.** Record 808 as the *measurement* PREMISE-141 named as open. This is the cheapest correct disposition and preserves the finding.
(b) **Answer claim (1) by documentation lookup, not by inference.** The emission conditions are a property of the CLI/SDK. Verifying the changelog entry (source 2) and reading claude-agent-sdk-typescript #366 would likely settle it in under an hour. **This is a decidable question and should not sit as UNTESTED.**
(c) **Add the attribution field (ALCOA+ "Attributable").** A terminal-state record with an actor-identity field admitting `human` / `runtime` / `unknown`, defaulting to `unknown`, converts the ambiguity from an interpretive problem into a recorded one. `unknown` is the honest default and is currently unrepresentable.
(d) **Do not re-open the 35.5% base rate on this ground.** The count of deliverable-less runs is invariant under the attribution question. If the base rate is to be re-opened it must be on a different argument.
(e) **Construct the discriminator before treating the marker as evidence in either direction.** Cross the marker against an independent record — host uptime, sandbox eviction log, session-lifetime cap. One such cross-reference is worth more than any further reasoning from the transcripts, which are the artefact under suspicion (PREMISE-096: no self-produced artefact may certify itself).

### Recommendation: PARTIALLY-CHALLENGED

Core proposition: **NO-CHALLENGE-FOUND, and externally corroborated in the item's favour.** Evidential inference and Critical grade: **CHALLENGED (Moderate)** on non-discrimination and on register duplication.

## STEELMAN

**Item:** PRESUMPTION-808

**Strongest counterargument (the strongest case *against* the item as filed, stated at full force):** The item presents as a new Critical discovery something the register already holds open by name, and it supports it with an observation that cannot support it. Take the evidence first. "No transcript contains a single typed human message" is offered as the ground for suspecting the marker. But this is a fleet of *scheduled* tasks: no run has a typed human message, ever, by construction. The observation is therefore a constant, and a constant has no discriminating power between the two hypotheses on offer. Under "a human interrupted through some channel that leaves no transcript entry" and under "the runtime emitted the marker spontaneously," the record looks identical. Whatever warrant the item has comes from somewhere else entirely — and it does have warrant, from the vendor's issue tracker, which the item does not cite because it did not look. Now take the register. PREMISE-141 was validated on 2026-08-05 from four transcripts all terminating at this exact marker, and it carries a load-bearing scope limit stating that the cause of `[Request interrupted by user]` **is undetermined** and that the premise "licenses no claim that the interruptions were faults rather than deliberate human stops." 15c excluded the interrupt-cause question deliberately, in writing. Eleven days later the same question returns as PRESUMPTION-808, graded Critical, with no reference to the premise that already holds it. That is not a new finding; it is the pipeline's detection layer rediscovering its own output, which is precisely the failure PRESUMPTION-812 in this same batch is about. The general form is worse: "attribute the fault to the actor rather than to the specification or the system" is *already* validated at PREMISE-146 clause (3) with a full literature base, so 808's insight is a specific instance of a held premise, not an addition to it. And the Critical grade does not survive inspection. It rests on the claim that the 35.5% base rate "was computed over the same misattribution." It was not. A run that stops at the marker delivered nothing, and it delivered nothing whether a human stopped it or the runtime did. Misattribution changes what the fleet believes about *why* those runs failed; it does not move the count by one. What remains, after all that, is a genuine and cheap defect — the terminal-state record has no field in which "the runtime stopped this" is representable, and `unknown` is not an available answer. That is a schema fix on the ALCOA+ "attributable" pattern, costing an afternoon. Grading an afternoon's schema fix as Critical while PRESUMPTION-812 reports that closure capacity is the binding constraint is not rigour; it is the detection layer competing with itself for a queue it has already saturated. Finally, there is a cost to the correction that the item does not price. Reclassifying the fleet's only mute-cause signal as untrustworthy, without simultaneously supplying a replacement discriminator, converts every mute run into an open investigation with no artefact capable of closing it. The alarm-management and cry-wolf literature measures exactly this: as a signal's perceived reliability falls, verification-before-action rises and response degrades. An unreliable signal with no substitute is worse than a reliable-enough signal with a caveat.

**What would need to be true for C2A2 to be safe:** Three things, in order. (1) The **emission conditions must be established from the runtime's documentation or source**, not from transcript inference — this is a decidable question with a documented answer path, and until it is asked the item should not be graded at all. (2) The terminal-state record must carry an **attribution field with `unknown` as its representable default**, so that the fleet's uncertainty is stored rather than re-derived every time someone reads a marker. (3) Any downstream use must respect **PREMISE-141's symmetry**: the cause is undetermined *in both directions*, and a standing bias toward "machine fault" is the same error as the standing bias toward "human stop." If all three hold, 808 is discharged and no Critical exposure remains — the failure count is unchanged, the causes are honestly recorded as unknown where unknown, and the fleet has stopped re-deriving the same open question every eleven days.

**How to test:** (1) **The documentation test, decisive and cheap.** Read the Claude Code changelog entries and `claude-agent-sdk-typescript` issue #366 to establish whether non-user emission paths are vendor-acknowledged. Predicted result under 14b's hypothesis: at least one acknowledged path. Predicted under the null: the marker is emitted only on explicit client abort, and the fleet's three cases have some other explanation. **This test was not completed this run and is the single highest-value outstanding action on this item.** (2) **The discrimination test.** For each run terminating at the marker, cross-reference host uptime, sandbox eviction records and session-lifetime caps at the marker's timestamp. A machine cause leaves a second trace outside the transcript; a human stop does not. This is the observation that has a likelihood ratio, and the transcripts do not. (3) **The invariance check on the base rate.** Recount deliverable-less runs with all marker-terminated runs excluded, then with all of them included as machine failures. If the two counts are the same — and they should be — the claim that the base rate was "computed over the misattribution" is retired and the Critical grade with it. (4) **The register test.** Before minting, run the PREMISE-105 duplication check against PREMISE-141, PREMISE-146 and PREMISE-139. My grep says it will hit. If it does, the disposition is route-to-141, not mint.
