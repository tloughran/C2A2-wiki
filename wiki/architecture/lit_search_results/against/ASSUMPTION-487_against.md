  Sources:
    1. SQLite documentation, "How To Corrupt An SQLite Database File" (sqlite.org/howtocorrupt.html, retrieved 2026-07-21). Copying or backing up a database file while it is being written is a canonical, documented cause of the "database disk image is malformed" error. This inverts the item's central inference: the fact that the errors come from a point-in-time backup is evidence FOR the mid-write-artifact hypothesis, not against it. A file copied mid-transaction is expected to be malformed even when the live database is perfectly intact.
    2. Corroborating vendor documentation (Ahsay Backup, "SQLite Error: Database Disk Image is Malformed"; DB Pro, "Fix: database disk image is malformed"; retrieved 2026-07-21). Both list "creating a backup of the database while it is currently in use" and "copying the database while it is being written" among the standard causes, alongside power loss and bad sectors.
    3. SQLite documentation, "Recovering Data From A Corrupt SQLite Database" (sqlite.org/recovery.html, retrieved 2026-07-21). Perfect restoration is "the exception"; recovered databases are usually defective — some content permanently unrecoverable, and previously deleted content can be resurrected from freelist pages and reintroduced as live rows. Challenges any recovery-based remedy.
    4. Sling Academy, "SQLite Error: Cannot Execute VACUUM on Corrupted Database" (retrieved 2026-07-21). VACUUM (and hence VACUUM INTO) fails on a genuinely corrupt database. The item's implied rebuild path is therefore self-testing: if VACUUM INTO succeeds, the database was not corrupt.
    5. Silent-failure literature: "Silent Failure in LLM Agent Systems" arXiv:2606.08162 and "Detecting AI Agent Failure Modes in Production" (Latitude, retrieved 2026-07-21). A pipeline that runs green while producing no output is the canonical silent failure; staleness alone does not distinguish a stopped writer from a writer that is running and failing to commit.

  Strength of challenge: Strong
  Summary: The item's load-bearing inference runs backwards. It argues that because the errors were observed in a point-in-time backup rather than in the live file, the corruption must be real rather than a mid-write artifact. SQLite's own corruption documentation lists copying or backing up a database while it is being written as a standard cause of exactly this error class — so a backup that reports malformation is the expected observation when a live writer is mid-transaction, and it is weak evidence for on-disk corruption. That in turn undermines the second half of the claim: if the corruption may be a backup artifact, the writer may well be running, and "the writer has stopped" is an inference resting on the same reversed reasoning. The two halves of the claim are also in tension with each other — a stopped writer would not produce mid-write artifacts, so the item needs the corruption to be real in order for the staleness story to cohere, and it is the reality of the corruption that is in doubt. All of this is settleable in minutes by the item's own test, which should be run before any recovery action, because recovery is lossy and can resurrect deleted rows.
  Specific risks: A recovery or rebuild is performed on a database that was never corrupt, and the .recover path silently reintroduces previously deleted content as live rows, injecting stale records into open-story with no marker. Second risk: the writer is diagnosed as stopped and decommissioned or restarted when it is in fact running and failing at commit, so the real fault survives the fix and 14.6 days becomes 30. Third risk: the backup procedure itself is the corrupting agent and remains in place, regenerating the same alarm indefinitely.
  Mitigations available: Run PRAGMA integrity_check against the LIVE database Mac-side before touching anything — this is the item's own stated test and it discriminates cleanly. Independently confirm writer state by process inspection and by checking mtime and WAL/journal file presence, not by inferring from staleness. Fix the backup method regardless of outcome: use the SQLite backup API, VACUUM INTO, or .dump against a live connection rather than a filesystem copy. If integrity_check does report corruption, prefer VACUUM INTO (which fails loudly on a corrupt file) over .recover, and if .recover is used, treat lost_and_found and any resurrected rows as suspect.

It reasons that because the malformation errors came from a point-in-time backup rather than the live file, this cannot be a mid-write artifact — but SQLite's normative corruption documentation lists copying or backing up a database while it is in use as a canonical cause of precisely the "database disk image is malformed" error, and multiple vendor troubleshooting guides repeat it. This matters because the two halves of the claim depend on each other: if the corruption is a backup artifact, the writer was probably active at backup time, which contradicts "the writer has stopped," and the staleness then needs an independent explanation. There is also a compounding hazard in the remedy space: SQLite states plainly that perfect recovery is the exception, that some content is typically permanently lost, and that deleted rows sitting in freelist pages can be resurrected and reintroduced as live data. Running a recovery against a database that was never corrupt would therefore be strictly damaging — it would inject stale deleted records into open-story with no provenance marker, in a system that already has six unresolved counting disputes.
    What would need to be true for C2A2 to be safe: That integrity_check is run against the live file before any recovery action, and that the backup method is changed to a transaction-safe one regardless of the result, so the alarm is not regenerated.
    How to test: Three commands, minutes, no risk. (1) PRAGMA integrity_check on the live open-story.db Mac-side. (2) Check for a live writer: process list, plus file mtime and the presence of -wal/-shm or -journal files. (3) Attempt VACUUM INTO on a copy — it fails on genuine corruption, so success is itself a negative corruption test. If integrity_check returns ok, the corruption was a backup artifact and the entire diagnosis needs rewriting.
