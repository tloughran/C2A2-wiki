  Strength of challenge: Strong

  Summary: This presumption is refuted about as cleanly as anything in this pipeline can be. The negation — that a pathname is not a stable reference to a file object, and resolves anew at every use — is not a research finding but a design axiom of systems security, and the class of bugs it names has produced privilege escalations in sudo, at, crontab and dozens of other utilities over four decades. It is not historical: a TOCTOU symlink vulnerability was patched in the mainstream Python `filelock` library in 2025 with a CVE, and the class has been carried explicitly into agent systems by 2026 work on atomicity for browser-use agents. Content-addressable storage exists as an industry-wide paradigm for the single reason that location does not identify content, and build systems have a standard name — "stale cache hit" — for the failure that path-inferred dependence produces. The one caution worth stating is that most of this literature is written against an adversary, and C2A2 plausibly has none; but the agent-atomicity work and the Bazel evidence both show the failure does not require malice, only a check-then-use gap over mutable state, and the Bazel study found that zero of seventy projects built specifically to close that gap actually closed it. The presumption's real damage is that it is silent: because no run states it, no run tests it, and three separate traps in one night all reduced to this single unexamined identity claim.

  Specific risks:
    - False-clean verdicts (the concrete instance already observed): a run trusts a stale artifact as its own and reports a scan result it never produced. This failure's signature is a *pass*, so no failure-detector sees it.
    - Silent cross-run contamination: two runs writing to the same conventional path produce a last-writer-wins artifact that a third run reads as authoritative, with no record that two authors existed.
    - Correctness laundering: an artifact from an older, possibly obsolete code path is consumed as current, so a fixed bug can appear to persist or a persisting bug can appear fixed, depending on which stale file survives.
    - Unbounded blast radius: because the presumption is unstated, its scope is unknown. Every read of a conventionally-named file anywhere in the pipeline is a potential instance. Three traps found in one night is a sample, not a census.
    - No adversary required: the Bazel result shows path-dependence persists even where engineering effort is directed at removing it, so "we have no attacker" is not a defence.
    - Detection is structurally hard: the check and the use are separated in time, so any verification that itself uses the path re-incurs the same gap. Only content-level verification closes it.

  Mitigations available:
    - Content-address every artifact. The producing run writes a hash (and its own run identifier) alongside or inside the artifact; the consuming step verifies before parsing. This is the direct and complete remedy and it does not require an adversary model.
    - Write to a unique per-run path — run identifier in the filename — and never to a shared conventional path. This makes cross-run collision structurally impossible rather than merely unlikely.
    - Atomic create-then-rename with O_NOFOLLOW / O_EXCL semantics, following the filelock patch pattern. Never open a path for output that may already exist.
    - Embed authorship in the artifact body: run ID, timestamp, and the input set examined. A consumer that finds a mismatched run ID fails loudly instead of trusting silently.
    - Eliminate the check/use gap where possible: operate on an open file descriptor obtained once, rather than re-resolving a path, per the standard TOCTOU remedy.
    - Audit for the presumption's other instances: grep the pipeline for every read of a conventionally-named intermediate artifact and treat each as an unverified identity claim until content-addressed.

  STEELMAN:
    Item: PRESUMPTION-837
    Strongest counterargument: The presumption is not merely unproven, it is the negation of a principle that systems engineering settled decades ago. A pathname is a name that gets resolved, separately, at every single use; nothing about a successful resolution tells you who wrote what is now there, or when, or whether it is the thing you wrote a moment ago. Four decades of privilege escalations in sudo, at, crontab and their relatives are the accumulated cost of assuming otherwise, and the assumption is still costing: a symlink TOCTOU was patched in mainstream Python tooling in 2025 with a CVE attached. Content-addressable storage exists as a paradigm for exactly one reason, that location does not identify content; build systems have a standing name, "stale cache hit", for the incorrect result that path-inferred dependence produces. And the escape route of "we have no adversary" does not hold, because an empirical study of seventy projects using the toolchain specifically designed to remove filesystem-state dependence found that not one of them achieved it — the failure needs only a mutable filesystem and a gap between writing and reading. What makes the presumption dangerous in C2A2 specifically is that it is unstated, so its scope is unmeasured; three traps in one night are a sample from a population nobody has counted.
    What would need to be true for C2A2 to be safe: (a) Every artifact path would have to be written by exactly one run, ever — enforced structurally by embedding a run identifier in the path, not by convention; (b) no run could ever read an artifact it did not itself create within the same execution, or if it must, it verifies a content hash written by the producer; (c) writes would have to be atomic create-then-rename with O_EXCL/O_NOFOLLOW so that an existing file at the target is an error rather than a silent substitution; (d) the *scope* of the presumption would have to be enumerated — every read of a conventionally-named intermediate is an instance, and until they are counted the risk is unbounded rather than small.
    How to test: Two direct experiments. (1) Census: enumerate every point in the pipeline where a run reads a file it did not create in the same process, and count them. That number is the number of live instances of this presumption, and the item's "three traps" should be compared against it. (2) Injection: for each such point, pre-place a syntactically valid but semantically wrong artifact at the expected path and run the pipeline. Every case where the run completes without complaint is a confirmed instance; every case where it fails is already protected. This converts an inferred presumption into a measured attack surface in one pass, and requires no new architecture to run.
