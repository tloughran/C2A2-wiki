### Challenging evidence found: Yes (partial — against the remedy class and against the value of detection at this base rate, not against the diagnosis)

### Sources

1. **systemd `WatchdogSec` guidance and practitioner analysis of heartbeat false negatives** (OneUptime, "How to Configure systemd RestartSec and WatchdogSec"; HostMyCode systemd watchdog guidance, 2026). [verified this run — snippet level, practitioner documentation, not research] — The decisive challenge to the remedy. The named failure mode is stated explicitly: "a common failure mode is sending watchdog heartbeats **unconditionally** — if code keeps sending `WATCHDOG=1` while it's stuck, systemd has nothing to act on," and the prescribed fix is to "tie heartbeats to a cheap internal signal: queue progress, loop ticks, thread heartbeat, or a dependency probe with a hard timeout." The distinction is between **liveness** (the process exists) and **progress** (the process is doing its work). `morning-system-health` reached two tool calls before stopping: it was live. Any heartbeat emitted at process start, at launchd invocation, or per tool call would have been emitted, and the switch would have stayed armed.
2. **The "zombie" failure class in service supervision** (same source family; Red Hat Customer Portal on watchdog zombie processes). [verified this run — snippet level] — "A 'zombie' scenario occurs when the service process is alive but stuck — not processing requests, stuck in a lock, or in an infinite loop that is not doing useful work." "Process checks alone miss zombie sessions." This is the fleet's 39-of-110 population, and the item's own worst case — "hanging 5.1 days until the Mac slept" — is a hang, not a non-start. A detector designed around absence-of-invocation is aimed at the wrong tail of the distribution.
3. **Dead-man's-switch practice and the common-infrastructure warning** (cloudonaut, "Dead man's switch with CloudWatch"; Nanit Engineering, "Who watches the watchers?"; Seif Rajhi, "Securing your monitoring stack with a dead man switch"; watchflow, "Why cron jobs fail silently"). [verified this run — snippet level, vendor/practitioner blogs] — Establishes that the diagnosis is orthodox and the countermeasure is standard: "silent failures in cron jobs don't throw errors — they just stop doing the work"; a dead man's switch "serves as an independent watchdog, tasked with keeping an eye on the monitoring system." Crucially, the rule these sources converge on is **externality, not documentation**: "Running monitoring on the same infrastructure as your jobs creates a single point of failure. **Use an external service.**" The fleet has no external plane; every candidate watcher in the architecture is another launchd agent on the same Mac, subject to the same sleep, the same MCP unavailability, and the same session-interruption mechanism. A watcher built inside C2A2 does not satisfy the one condition the literature insists on.
4. **Layer of Protection Analysis — independence and common-cause failure criteria** (Primatech, "Qualifying safeguards as IPLs for LOPA"; aeSolutions, "Pitfalls in IPL selection"; AIChE/CCPS LOPA materials). [verified this run — snippet level, consultancy and professional-body material summarising CCPS practice] — The formal statement of what the fleet cannot currently satisfy. An independent protection layer's effectiveness must be independent of "the occurrence or consequences of the initiating event, the failure of any component of an IPL already credited for the scenario, or conditions that caused another IPL to fail," and — the sharp rule — "**credit should be taken for only one of the IPLs where they are affected by common cause failure.**" Under this rule, `morning-system-health` and the runs it watches are a single layer, not two. Adding a third launchd agent adds no credit. This is the strongest available *challenge to the assumption's implicit optimism* that a fix exists inside the fleet's boundary, and it is also the literature that says how the regress terminates: it terminates at an *independent, auditable* layer, which means outside.
5. **Deming — "Inspection does not improve the quality, nor guarantee quality"; "Inspection is too late. The quality, good or bad, is already in the product"; Point 3, "cease dependence on inspection to achieve quality."** (W. Edwards Deming Institute quotation pages; *Out of the Crisis*.) [verified this run for the quotations via deming.org; the book itself **canonical, NOT re-verified**] — The economic challenge to the whole detection framing. A 35.5% terminal-failure rate is not a monitoring problem; it is a process-capability problem. A detector layered on a process with that failure rate produces roughly one true alarm every three runs and does nothing to reduce the rate. Deming's kp rule formalises the point: for a process in statistical control the economic optimum is *inspect all or none*, never a partial regime — and 35.5% is far above any threshold at which partial inspection is the right answer.
6. **Alarm-load evidence from an adjacent field** — clinical decision support override rates of **49–96%** (Wilson et al., "Alert fatigue measurement in clinical decision support: a systematic review," 2026, PubMed 42148822). [verified this run — snippet level, abstract and summary only] — Included as a boundary condition on the remedy. A detector that fires on a third of all runs, into an environment with no reader for eleven days, is being built into the regime where the alerting literature documents systematic disregard. The relevance is limited (different domain, human recipients) and is flagged as such.

### Strength of challenge: Moderate

### Summary

The diagnosis survives entirely. Monitoring practice names this failure — silent cron failure, watcher on shared infrastructure — and prescribes an external dead-man's switch. Two challenges land on what follows from it. First, the remedy class is aimed at the wrong failure: the observed run *started* and then stopped, and the documented failure mode of heartbeat monitoring is precisely a process that keeps signalling while stuck. A switch armed by invocation would have shown green on 2026-08-14. What the literature prescribes instead is a heartbeat bound to *progress* — a queue counter, a step index, a per-step token — so that the signal stops when the work stops rather than when the process dies. Second, the independence condition that makes any watcher creditable is one the fleet cannot currently meet. LOPA's rule is explicit: where two layers share a common cause, credit only one. Every candidate watcher inside C2A2 runs under the same launchd on the same machine and dies to the same sleep, so building a third agent to watch the second buys no assurance, only an artefact that reads as if it did. Third, and least comfortable: at a 35.5% terminal-failure rate the detection framing is the wrong economics. Deming's position — inspection is too late, and for a process in control the optimum is all-or-none — implies the fleet's effort belongs on why 39 of 110 runs never finish, not on a better instrument for counting them. Finally, the specific literature the queue asked for does not appear to exist: I found no measured failure rate for self-hosted stall detectors, which means the fleet's own 110-run figure is currently the best datum on the question.

### Specific risks

If the item is acted on with a same-plane watcher, the fleet acquires a fourth launchd agent whose green state is evidence of nothing, and — worse — whose existence retires the concern. This is the failure the item itself describes, reproduced one level up, and it is the specific outcome LOPA's common-cause rule exists to prevent.

If the item is acted on with an invocation-keyed heartbeat, the fleet gets a detector that would not have caught the 2026-08-14 case, the 5.1-day hang, or `openstory-agents-telemetry-refresh`'s interruption before step 5 — all three of which are stalls of a *started* process. The detector would report healthy through the fleet's dominant failure mode.

If the item is dismissed, the hazard is exactly as stated and is compounded by the second case: `REFRESH_STATUS.md`'s absence is the *only* signal of a silent stall, and absence is unattributable. A missing file is consistent with a stall, a permissions change, a path change, a rotation, a sleeping machine, and a clock skew. Absence-as-signal is a low-specificity detector even when it works, and this one did not get written at all.

A further risk crossing to other items in this intake: whatever the fleet builds, its sampling frame will be the set of runs that reached the recording surface. See the SYSTEMIC-RISK-FLAG below.

### Mitigations available

(a) **Bind the heartbeat to progress, not to existence.** Emit a monotonically increasing step index or completed-unit count; the switch trips on *no increment within N minutes*, not on *no signal*. This is the documented fix for the unconditional-heartbeat failure and it is the only mitigation here that would have caught the observed case.
(b) **Put the switch on a different plane.** An external check-in URL (the cron-monitoring services in source 3 exist for this) or any process not started by the same launchd satisfies the independence condition. If no external plane is acceptable, then under LOPA's rule the fleet should record that it has **one** protection layer, not two — an honest count is worth more than an uncreditable second layer.
(c) **Make absence attributable.** Where absence must remain the signal, write the artefact *first* with a `status: IN-PROGRESS` line and update it, so that a stalled run leaves a dated stub. This converts "file missing — cause unknown" into "run started at T, never completed," which is a diagnosis rather than a prompt to guess.
(d) **Attack the 35.5%.** Deming's point applies literally: the highest-value action is not a better detector but a bounded execution model — hard timeouts, checkpointed resumption, and a machine that does not sleep mid-run. A fleet with a 3% hang rate needs a much weaker detector than one with a 36% hang rate, and gets more from every other instrument it owns.
(e) **Treat the 110-run measurement as the fleet's own contribution.** Since the literature appears not to carry this figure, keep measuring it and publish the denominator with it; it is the fleet's best evidence and the only trend line that will show whether (d) worked.

### Recommendation: PARTIALLY-CHALLENGED

## STEELMAN

**Item:** ASSUMPTION-1068

**Strongest counterargument:** The item has correctly named a real defect and is about to buy the wrong fix twice over. Its framing — the reporter died, so the death went unreported — points naturally at a dead-man's switch, and every source in this field will sell you one. But read the failure again: `morning-system-health` *ran*. It made two tool calls. It was alive, and it was not making progress. The documented, named failure mode of heartbeat monitoring is exactly this — code that keeps sending `WATCHDOG=1` while stuck gives the supervisor nothing to act on — and the fleet's own worst case, a run hanging 5.1 days until the Mac slept, is the same shape. An invocation-keyed switch would have shown green through every incident the item cites. The second error is deeper. LOPA's independence rule says a protection layer earns credit only if its effectiveness is independent of whatever caused the other layer to fail, and where common cause exists you may credit only one layer. Every watcher C2A2 can build is another launchd agent on the same Mac, dying to the same sleep and the same session interruption. Building it does not add a layer; it adds an artefact that *reads* as a layer, which is strictly worse than an honest count of one, because it retires the concern without discharging it. And beneath both: 39 of 110 runs never finished. That is not a monitoring gap, it is a process running at 64.5% capability, and Deming's answer to it is not a better inspector. Inspection is too late; the quality is already in the product. The fleet's instinct to instrument the failure rather than fix it is the pattern the whole quality tradition was built to interrupt.

**What would need to be true for C2A2 to be safe:** Either (a) the watcher runs on a plane that does not share launchd, the machine's sleep state, or the MCP surface with the watched population — an external check-in endpoint being the cheapest form — **and** its trigger is bound to a progress signal rather than to invocation; or (b) the terminal-failure rate is driven low enough that absence-based detection has a workable base rate, at which point a weaker detector suffices. With neither, the item's hazard is live. With a same-plane, invocation-keyed watcher and neither, the hazard is live *and* covered.

**How to test:** Three cheap experiments. **One:** take whatever detector is proposed and run the 2026-08-14 case against it — start `morning-system-health`, let it make two tool calls, kill it. If the detector reports healthy, it is invocation-keyed and does not address the fleet's dominant failure mode. This is a five-minute test and it should gate any implementation. **Two:** test the independence claim directly by sleeping the Mac during a run and observing whether the watcher reports. If it does not, the two are one layer and LOPA says credit one. **Three:** partition the 39 non-finishing runs into *never started* versus *started and stalled*. The item's remedy is well aimed at the first partition and badly aimed at the second, and the ratio between them decides which fix is worth building. The fleet already has the transcripts to compute it and it needs no attendance.

## SYSTEMIC-RISK-FLAG

**Date:** 2026-08-15
**Affected items:** ASSUMPTION-1068, ASSUMPTION-1069, ASSUMPTION-1075, ASSUMPTION-1077 (peripherally ASSUMPTION-1070)
**Common vulnerability:** **Every instrument these four items propose draws its sample from the set of runs, artefacts or decisions that reached a recording surface — a frame generated by the very process the instrument is meant to audit.** 1068's watcher runs on the plane it watches; 1069 would count deliverables produced by runs that survived to produce them; 1075's checks report on pairs where the check did not silently skip; 1077's override rate is computed over exactly the items some upstream filter routed to the human. In each case the failures of interest are the ones that never entered the frame.
**Literature basis:** PCAOB **AU 350 / AS 2315** states the disqualifying condition in one sentence — "an auditor would **not** be able to detect understatements of an account due to **omitted items** by sampling the **recorded** items. An appropriate sampling plan for detecting such understatements would involve selecting from a source in which the omitted items are included" [verified this run]. **Priest & Klein (1984), "The Selection of Disputes for Litigation"** — outcome rates over a selected set are uninformative about the underlying population; the acknowledged corollary is that appellate reversal rate is "an imperfect proxy for quality" [verified this run, snippet level]. **LOPA / CCPS independence and common-cause rules** — credit only one layer where common cause applies [verified this run, snippet level].
**Risk level:** Critical
**Recommendation:** Before any of these four instruments is built, state its **sampling frame** and the **source from which the frame is drawn**, and check that the source is not produced by the audited process. For 1068 and 1069 there is a frame that satisfies this and the fleet already owns it: the **launchd schedule** — the declared set of runs that *should* have occurred, authored independently of whether any of them ran. Reconciling against the schedule rather than against outputs is the single change that repairs the frame for both. For 1077 the equivalent is **seeded defects**: without items of known status injected into the population, no override statistic has a denominator that means anything.
