  Challenging evidence found: Partial

  Sources:
    1. Beyer, B., Jones, C., Petoff, J. & Murphy, N.R. (eds.) (2016). *Site Reliability Engineering*, Chapter 6, "Monitoring Distributed Systems." O'Reilly/Google. — The strongest challenge, and it inverts the item's framing. The SRE position is that black-box, symptom-oriented monitoring — "is the system producing the thing it exists to produce, right now" — is what should page a human, and that white-box internal-state monitoring is for diagnosis. An artifact-recency check is textbook black-box monitoring: it observes the output the run exists to produce. On this view the watchdog is measuring the *right* thing, and "did the process terminate" is an internal-state question of secondary interest. A run that is still executing but has already written today's artifacts has, symptomatically, delivered; a run that terminated cleanly having written nothing has not, and the exit-status check 14b implicitly prefers would pass it.
    2. SRE Chapter 6 and the alerting-discipline literature (Rabenstein & Volz, "Alerting for Distributed Systems: A Tale of Symptoms and Causes," SREcon16 Europe). — Direct challenge to the remedy rather than the diagnosis. The stated principle is that every page must be actionable and that effort should go into catching symptoms rather than causes. A "still running" state is a cause-class signal with no defined action: a long-running task is normal until it is not, and the threshold at which it becomes abnormal is exactly what the watchdog has no basis to set. Adding the symbol 14b asks for, without a duration threshold, converts a two-way verdict into a three-way one in which the third branch is not actionable — which the literature identifies as a principal driver of alert fatigue.
    3. Two Generals' Problem, and its consequence for completion signalling (Akkoyunlu, Ekanadham & Huber 1975; Gray 1978; standard treatment). — Challenges the *superiority* of the remedy. Exactly-once acknowledgement over a channel that can lose messages is impossible; this is why practical systems settle for at-least-once delivery plus idempotency rather than a reliable completion signal. A sentinel-on-exit can be lost, can be written by a run that then fails during cleanup, or can be absent from a run that completed all substantive work and was killed at teardown. Explicit completion signalling is therefore *also* a proxy with its own false-green and false-red modes; the item presumes a clean alternative that the literature says does not exist.
    4. Chandra & Toueg (1996), JACM 43(2), read against the item. — The failure-detector result is standardly read as licensing unreliable detectors, not as condemning them: useful failure detectors are necessarily unreliable, and systems are built to tolerate that rather than to eliminate it. The existence of an indistinguishability argument against artifact-freshness is not by itself an argument that artifact-freshness is the wrong detector — only that its accuracy class must be stated. That is a documentation defect, materially smaller than the "category error" reading the item invites.
    5. Deduplication of concerns — freshness monitoring practice (data-observability freshness SLAs; Datadog data-observability documentation, 2025-2026). — Partially challenging on scope: freshness monitors are deployed at scale precisely because, for pipelines whose purpose is to produce artifacts, artifact age is the highest-signal cheap indicator available, and the documented failure mode is staleness (artifact too old), not the item's failure mode (artifact fresh, run unfinished). The item generalises from a failure direction the operational literature treats as the rare one.
    6. Empirical gap, reported as a challenge to the item's evidentiary standing: no source was found reporting a measured false-green rate for artifact-freshness health checks, nor any establishing that the fresh-artifact-unfinished-run case is common. The item's settling quantity is unmeasured in the literature as well as in C2A2, and its supporting instance is n=1.

  Strength of challenge: Moderate

  STEELMAN:
    Item: PRESUMPTION-592
    Strongest counterargument: The watchdog is not making the error attributed to it. It is a black-box monitor answering a symptom question — "did today's outputs appear" — and answering it correctly. The item reads its PASS as a claim about process termination, but nothing in the watchdog asserts termination; the inference "PASS therefore the run completed" is made by the *reader*, and the defect, if any, is in the verdict's label rather than in its evidence. Meanwhile the proposed remedy is worse than it looks. Exit status and sentinel files are not ground truth — the Two Generals result guarantees no completion signal is reliable — so the change trades one proxy for another while adding a third verdict branch whose action is undefined, and undefined branches are the documented origin of alert fatigue. The one observed instance is a run that was still executing *and had already produced its artifacts*: on the symptom criterion that is a success, and treating it as a false green requires assuming that late-stage work matters more than the artifacts already delivered — an assumption the item states nowhere. Finally, the analogy to PREMISE-110's stuck-at fault class is imperfect in the direction that matters: a stuck-at sensor reports the *same* value indefinitely, whereas a fresh artifact is by construction new evidence, produced today, by the run in question.
    What would need to be true for C2A2 to be safe: (i) the substantive work of a run is reliably complete by the time its artifacts are written — i.e. artifacts are the last thing a run does, not the first; (ii) the failure mode of interest is absence or staleness of artifacts, not partial production; (iii) readers of the watchdog's PASS understand it as a symptom verdict and not as a termination claim, which requires the label to say so.
    How to test: Two in-house measurements, both cheap. (a) For the last N scheduled runs, compare artifact write time against task terminal time from the scheduler's own record; the distribution of the gap tells you directly how often, and by how much, PASS precedes termination. (b) For runs that terminated in error, check whether their artifacts were nonetheless fresh at check time — this is the false-green rate the item names, and it is the one that matters, since a fresh artifact from a *failed* run is the damaging case and a fresh artifact from a still-running run is arguably not.

  Specific risks: The item's risk claim ("the watchdog is the only layer asserting fleet health") holds, but the challenge relocates the risk. Acting on the item as stated would add a "still running" branch and treat exit status as authoritative; if C2A2 then reduces its attention to artifact production, it acquires the opposite failure — a run that exits cleanly having produced nothing passes the new check and fails the old one. Both checks are needed; the item argues as if one replaces the other.

  Mitigations available: (a) Relabel rather than re-engineer: change PASS to name its evidence ("artifacts present and fresh") so the termination inference is not silently available to readers. This addresses the whole of the documentation defect at near-zero cost. (b) Add terminal state as an *additional* field, not a replacement verdict, and keep the artifact criterion as the paging signal per SRE Chapter 6. (c) Set a duration threshold before introducing a "still running" state, so the third branch is actionable. (d) Measure the write-to-terminate gap before changing anything.

  Recommendation: PARTIALLY-CHALLENGED
