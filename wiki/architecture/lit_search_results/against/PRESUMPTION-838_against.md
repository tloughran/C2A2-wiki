  Original statement: That a workaround for a missing capability inherits the safety properties of the capability it replaces. Three runs substituted host access for an absent mount; all three died there. The one run that declined the substitution completed.

  Reading challenged: The presumption itself — that substituting a route preserves the safety envelope of the route it replaces. METHODOLOGICAL CAVEAT on the item's own evidence [15b's analysis, flagged as such]. — The item's evidential base is four runs on one day: three substituted and died, one declined and completed. With n=4 and no randomisation, the substitution decision is confounded with everything else that distinguishes those runs, most obviously with whatever made three runs willing to substitute and one unwilling. A run cautious enough to decline a substitution is plausibly cautious in other ways that independently predict completion. The 3/1 split is consistent with the presumption being false; it is also consistent with a selection effect, and nothing in the item distinguishes them.

  Strength of challenge: Strong (on the presumption), with a real counter-position on the policy implication and a real weakness in the item's own evidence.

  Summary: No located source supports the presumption, and the best-studied empirical case refutes it in detail: a field study of barcode medication administration found fifteen distinct workaround types with thirty-one causes, classified precisely as omitted steps, out-of-sequence steps, and unauthorised steps — that is, as the systematic shedding of the checks that constituted the original path's safety. The complementary e-prescribing incident analysis names the mechanism, "dropping parts of the process due to high workload", and adds automation surprise, which is what happens when a run's error handling was written for a route it is no longer taking. Vaughan's normalisation of deviance supplies the longer arc: a substitution that succeeds once is what licenses the next, so the presumption is the seed of a drift rather than a one-time error. Two honest qualifications belong in the record. First, the Safety-II tradition holds that workarounds are also the mechanism by which systems absorb conditions their designers did not anticipate, so "substitution is unsafe" does not entail "forbid substitution" — it entails "make the substitution visible and bounded". Second, the item's own evidence is four runs on one day with the substitution decision confounded with run disposition; the direction is right but the effect is not established by these data.

  Specific risks:
    - Silent envelope loss: the substituted route lacks checks the original carried, and because the substitution is unstated nobody knows which checks were lost. This is worse than a known-degraded mode.
    - Error handling aimed at the wrong failure set: automation surprise means the run's recovery logic was written against the original route's failure modes. When the substitute fails, it fails in a way the handler does not recognise.
    - Normalisation: the first successful substitution is the most dangerous event, not the failures. Three failures on one day are self-limiting; one success would have installed the belief.
    - Privilege as the fallback: the specific substitution here — host access for an absent mount — moves the run to a higher-privilege path. The safety difference is not neutral; a fallback that escalates privilege inverts the usual containment direction.
    - Suppression risk from over-correction: per Safety-II, banning substitution without supplying the missing capability converts a visible failure into an invisible one, since runs that need the capability will find another route and not record it.
    - Evidential fragility: acting hard on n=4 with a confounded predictor risks locking in a rule whose basis does not survive a larger sample.

  Mitigations available:
    - Make substitution an explicit, recorded state rather than an implicit choice. A run that substitutes must declare it, and the declaration must be visible downstream, so that the safety envelope is known to have changed.
    - Fail closed by default: absent capability should abort the run rather than trigger an unreviewed alternative route. This is what the one surviving run effectively did.
    - Never let a fallback escalate privilege. If host access is more privileged than the mount, it is not a fallback; it is a different operation requiring separate authorisation.
    - Supply the missing capability. Both the workaround literature and Safety-II converge here: workarounds are caused by a mismatch between work-as-imagined and work-as-done, and the durable fix addresses the mismatch, not the worker.
    - Instrument the substitution rate. Per the normalisation-of-deviance frame, the quantity to watch is successful substitutions, not failed ones.
    - Increase n before hardening the rule: track substitution/outcome over thirty days rather than one night.

  STEELMAN:
    Item: PRESUMPTION-838
    Strongest counterargument: A workaround is defined by what it omits. The best field data available — fifteen workaround types across thirty-one causes in barcode medication administration — classifies them as omitted steps, out-of-sequence steps, and unauthorised steps, which is to say that the safety properties of the original route were *constituted by* the steps a workaround drops. Nothing carries over, because there is nothing to carry: the safety was in the sequence, not in the outcome. The failure is then compounded by automation surprise, since the run's error handling was written against the original route's failure modes and cannot recognise the substitute's. And the presumption is worse than a single bad inference, because it is the entry point to normalisation of deviance: a violated constraint with no immediate consequence is what licenses the next violation, so the genuinely dangerous case is not the three runs that died but the first substitution that survives. In this instance the substitution also escalates privilege, replacing a scoped mount with host access, which means the fallback path is strictly less contained than the primary — the opposite of what a fallback should be.
    What would need to be true for C2A2 to be safe: (a) The substitution would have to be declared and recorded, so that downstream consumers know which safety envelope produced the artifact; (b) the fallback would have to be no more privileged than the primary, which host-for-mount is not; (c) the run's error handling would have to cover the substitute's failure modes, not the original's; (d) the rate of *successful* substitutions would have to be monitored, since success is what normalises; (e) — and this cuts against the item — the missing capability would have to actually be supplied, because per Safety-II a prohibition without provision converts a recorded workaround into an unrecorded one; (f) the n=4 evidence would need strengthening, since substitution choice is confounded with run disposition and a cautious run may complete for reasons unrelated to declining the substitute.
    How to test: Two things, one cheap and one that resolves the confound. First, add a mandatory `substituted_route` field to the run record and let it accumulate; after thirty days, the substitution/outcome table has enough n to test the association without relying on a single night. Second, break the confound directly: on runs where the mount is present, randomly withhold it for a subset and observe what each run does — whether it declines or substitutes — while holding the run's other properties fixed. That separates "runs that substitute are different runs" from "substituting causes failure", which the current evidence cannot do. Additionally, audit whether the host-access path is in fact more privileged than the mount; if it is, that finding alone justifies the gate independently of any outcome statistics.
