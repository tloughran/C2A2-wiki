### Strength of challenge: Moderate

### Summary

14b asked whether "would this test have failed on the broken version?" has an established name and method, and the answer is unambiguously yes, twice over: the industry calls it confirmation testing and specifies the fail-on-unfixed, pass-on-fixed pattern explicitly; the test-driven-development tradition makes the red step mandatory and treats a test never observed to fail as no test at all; and the research literature studies the same object as bug-reproducing or fail-to-pass tests, which is the convention Defects4J is built on. The base-rate evidence further undercuts the "single observation" framing: with under 1% of tests flaky in a large multi-project sample, a passing deterministic test is a decidable fact rather than a noisy draw, and demanding replication of a deterministic pass is a category error. So the presumption, as a general practice, is not merely defensible but is what the field does. The challenge stops at two places, both important. First, the flaky-test literature's other half is severe — 170 reruns for 95% confidence in a passing test's non-flakiness, and 47% of restarted failing builds passing on retry — so the base-rate defence holds only for tests demonstrably free of non-deterministic dependencies, and no one established that here. Second, and more interesting, 14b's charge of inconsistency does not survive scrutiny but its underlying instinct does. A verifier refusing to accept a zero without a negative control and a run accepting one passing adversarial test are not in conflict *provided* the adversarial test was demonstrated red first: a red-then-green test is a discrimination event, whereas an undemonstrated zero is a null reading, and the two genuinely warrant different treatment. If the two runs never observed the test failing on the broken generator, then their "adversarial test" is itself a null reading, and it is subject to the same demand the verifier made — at which point the fleet is not inconsistent, it is simply wrong in one place. Everything turns on a fact not in evidence.

### Specific risks

If the presumption holds and C2A2 tightens the standard anyway, the cost is small but real: replication of deterministic tests consumes budget with near-zero yield, and mutation-adequacy-style requirements are expensive to satisfy for a generator whose defect classes are already known. If the presumption fails in the specific way that matters — the adversarial test never having been demonstrated capable of failing — the risk is precisely inverted from what it appears: the fleet believes it has verified a fix and has in fact verified nothing, on an export path that 14b notes carries every review decision the human makes, with a defective page from the same generator still on disk as standing evidence that the failure class is live. That is a worse position than having no test, because a test believed to be protective suppresses further inquiry. The specific compounding risk is that two runs made the same inference on the same day, so a single unexamined premise was independently reinforced rather than independently checked.

### Mitigations available

(a) **Record the red.** Require every adversarial or bug-reproducing test to carry evidence that it was observed to fail on the unfixed artefact — a stored run log, a pinned commit, or a retained defective input. This is the confirmation-testing pattern as documented and costs one recorded execution. (b) **Keep the defective page.** 14b notes a defective page from the same generator is still on disk; that is not a liability but the ideal negative control, and running the current generator's test against it settles the question in one execution. (c) **Classify the test for non-determinism before invoking the base rate.** The 0.86% figure applies to tests without non-deterministic dependencies; a test touching time, ordering, concurrency, network, or filesystem state does not get that benefit and should be rerun. Making this a two-way classification rather than a blanket rule preserves the cheap case. (d) **Do not generalise from one adversarial input.** Confirmation testing establishes that *this* defect is fixed; it does not establish that the defect class is closed. If the generator's failure mode is parameterised, the test should be too. (e) **Reconcile the two standards explicitly in the contract**, since the fleet is currently applying different evidence bars in different places without stating why — and the reason, once stated, is defensible and worth writing down: null readings require positive controls, discrimination events do not.

## STEELMAN

**Item:** PRESUMPTION-791

**Strongest counterargument:** The item asks whether "would this test have failed on the broken version?" has an established name and method, and treats the absence of one as an open problem. It is not open. Industry QA vocabulary distinguishes confirmation testing from regression testing and specifies the exact pattern — a test that fails on the unfixed code and passes on the fixed code. Test-driven development has required the failing-red step as the first move of its cycle since 2002, on the explicit ground that a test never observed to fail is not yet a test. The research literature studies the same artefact as bug-reproducing or fail-to-pass tests, and the Defects4J benchmark is built on the convention. So the primitive exists, is free, is universally taught, and needed no discovery. The statistical framing is also wrong in its usual form: a deterministic test is not a sample, and the largest multi-project measurement available puts flakiness at 0.86% of tests, so replication of a passing deterministic test buys almost nothing. Against that, two runs accepting one adversarial pass are doing what competent engineers do, and the "inconsistency" with the nightly verifier dissolves once the two objects are distinguished — a demonstrated red-then-green pass is a discrimination event, while an unverified zero is a null reading, and only null readings need positive controls. Holding both standards at once is not incoherence; it is the correct discrimination, arrived at implicitly. **Where this stops:** the whole defence is conditional on a fact 14b's report does not settle — whether the adversarial test was ever observed to fail on the broken generator. If it was not, it is itself a null reading and the verifier's standard applies to it directly, and the fleet is not inconsistent but simply mistaken in one of the two places. The flaky-test literature adds a sharp boundary in the same direction: where non-determinism *is* present it is not marginal — 95% confidence that a passing test is not flaky has been estimated to require around 170 reruns, and 47% of restarted failing builds in a 75-million-build sample passed on retry — so the base-rate defence holds only for tests shown to be free of non-deterministic dependencies, which nobody showed.

**What would need to be true for C2A2 to be safe:** Two things, both checkable in a single execution each. (1) The adversarial test has been observed to fail on the unfixed generator, with that observation recorded rather than asserted. (2) The test has no non-deterministic dependency — no reliance on time, ordering, concurrency, network, or ambient filesystem state — so that one pass is decisive rather than a draw. Given both, a single pass is sufficient evidence and the two runs' inference is sound. Given neither, the item's worry is not merely live but understated, because a test believed protective suppresses the inquiry that would find the defect.

**How to test:** The generator's defective output is still on disk, which makes this the cheapest test in the queue. Run the current adversarial test against the retained defective page. If it fails, the test discriminates, the red is demonstrated retrospectively, and the presumption is vindicated for this instance. If it passes, the test does not detect the defect it was written for, the two runs verified nothing, and the finding is severe and immediate. Second, classify the test: enumerate its dependencies on time, ordering, concurrency, network and filesystem state. A test with none gets the 0.86% base rate and needs no reruns; a test with any should be rerun, and the rerun count is a matter for cost, not principle. Third, and cheapest of all: check the two runs' records for whether either observed a failing state before the pass. That is a question about the log, not about the code, and it decides which of the two readings above is correct.
