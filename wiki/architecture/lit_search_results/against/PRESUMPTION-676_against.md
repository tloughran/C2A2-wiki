A long-lived transaction executed as a sequence of short ones has **no atomicity across the sequence**; the system guarantees either that all complete or that *explicitly written compensating transactions* run to cancel the effects of the ones that already committed.   Strength of challenge: **Strong**

  Summary: This presumption is not merely challenged by the literature — it is the specific belief that forty years of distributed-systems work exists to correct. Garcia-Molina and Salem's sagas, Helland's apostasy, and the whole durable-execution industry are all responses to exactly one fact: when a process makes an external, non-transactional side effect and then dies, the side effect survives and the local record does not. There is no configuration in which this does not happen; the only variable is whether the system has compensations, intent records and idempotency keys to detect and repair it. C2A2's observed incident is the canonical instance: a Gmail label mutation committed to a system that shares no transaction with the vault, followed by an interruption, followed by no archive entry. The literature's prediction for what happens next is precise and matches 14b's inference — a future run reads the mailbox state, sees the decision as handled, and never processes it. Notably, C2A2's failure is on the *dangerous* side: the side effect landed and the record did not, which produces silent loss. Had the ordering been reversed (record first, effect second), the same interruption would produce a retry, which is recoverable.

  Specific risks:
    (a) **Silent loss of a human decision.** The specific risk 14b identifies is correct and is the literature's expected outcome. A decision email that has been unlabeled but not archived is invisible to both channels: absent from the "pending" view, absent from the archive. It is not delayed; it is gone.
    (b) **Unbounded, undetectable accumulation.** There is no instrument that reconciles Gmail label state against `review/archive/`, so the count of orphaned decisions is currently unknown and unknowable without a deliberate join. It may be one. It may not be.
    (c) **Wrong-direction ordering as a general pattern.** If the code performs external effects before recording locally in this one place, it likely does so elsewhere. Helland's rule is to write the intent first.
    (d) **Retry hazard on the other side.** Any remediation that adds naive retries without idempotency keys converts silent loss into duplicate application — the classic "did the call go through before the crash?" problem. The fix must be idempotent, not merely repeated.
    (e) **Compounding with PRESUMPTION-664/665.** Four scheduled sessions ended at `[Request interrupted by user]` on the same day. Interruption is not rare in this system; it is the observed weekday condition. The abnormal path is the normal path.

  Mitigations available:
    (a) **Write-intent-first.** Record the intended archive entry *before* calling `unlabel_message`. On restart, any intent record without a completion is replayed. This single reordering converts silent loss into a recoverable retry, and costs nothing.
    (b) **Idempotency key / natural key.** Key the archive entry on the Gmail message ID so replay is safe. Combined with (a), this is the full durable-execution pattern.
    (c) **A reconciliation sweep** (the compensating action in saga terms): periodically join Gmail label state against `review/archive/` and report messages that are unlabeled with no archive entry. This is a one-off query that would immediately size the existing damage — and should be run before any code change, because it is the only way to recover decisions already lost.
    (d) **Treat interruption as expected.** Yuan et al.'s prescription: write a test that kills the run between the external call and the local write, and assert that the next run recovers. Do not wait for the failure.

  Recommendation: **CHALLENGED (Strong)** — the presumption that an interrupted run leaves no partial state is contradicted by the foundational results of the field. Remediation is well-specified, cheap, and standard; the first action should be the reconciliation sweep, because it measures damage already done.

  STEELMAN:
    Item: PRESUMPTION-676
    Strongest counterargument: There is no version of this system in which the presumption holds. Gmail and the vault share no transaction manager, so by Helland's argument there is no atomic step that both mutates the label and writes the archive entry; and by the coordinated-attack impossibility, C2A2 cannot even *learn* whether a call it issued was applied once the connection is gone. Garcia-Molina and Salem wrote the saga paper in 1987 precisely because the alternative — assuming that an interrupted sequence leaves nothing behind — is false in every long-running system. The forty-year-old, industry-standard remedy is three lines of discipline: intent record before the call, idempotency key on the call, result record after. C2A2 used none of them and is now in the state the literature predicts. The sharpest part of the challenge is the ordering: C2A2's effect-before-record ordering fails *silently and unrecoverably*, whereas record-before-effect fails *loudly and recoverably*. This is not a tuning choice; it is the difference between a system that loses its human's decisions without telling anyone and a system that occasionally repeats an idempotent label operation. And because four runs were interrupted on a single day, the exposure is not a tail event — the system is currently operating with a lossy write path on its primary channel to its only human.
    What would need to be true for C2A2 to be safe: (a) every external side effect the system performs is idempotent *and* reconstructible from durable state — i.e., a later run can determine from the vault alone what should have happened; (b) a reconciliation pass exists and runs, so orphans are detected even when no one is looking; (c) interruption is rare — which the same day's evidence (four interrupted sessions) directly falsifies.
    How to test: One join, available now. List Gmail messages in the decision workflow that are currently unlabeled, and left-join against entries in `review/archive/`. Every row with no archive entry is an orphaned side effect. If the count is ≥ 1 the presumption is falsified with a concrete instance and the lost decisions are simultaneously recovered. Second test, for the general case: instrument the run to abort between the external call and the local write, then check whether the following run notices.
