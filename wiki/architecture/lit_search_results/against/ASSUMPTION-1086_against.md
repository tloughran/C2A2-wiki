### The arithmetic (performed this run on the item's own two figures)

The item's load-bearing sentence is "**the OK count is identical and the FAIL count moved 0 → 5**," from which it concludes "the failures did not begin today; the ability to see them did." Take the two readings as given:

- **2026-08-05 baseline:** 78 OK / 4 WARN / 0 FAIL → **82 checks**
- **2026-08-15 reading:** 78 OK / 1 WARN / 5 FAIL → **84 checks**

**The two readings have different denominators.** The identical OK count is a coincidence over two different check populations, not a controlled comparison, and it cannot be — the item states in the same breath that the instrument was rebuilt, that the old one "knew nothing about launchd," and that ASSUMPTION-1087 records the new contract prohibiting the old enumeration method and the mtime check. An instrument that newly enumerates 11 launchd agents and newly refuses mtime comparison is measuring a different thing. **This is PREMISE-105 exactly** — "a definitional change breaks a series" — applied to the fleet's own health series, and PREMISE-101 — "counts are properties of a (scope, method, time) reading."

Two consequences follow, and they cut in opposite directions:

1. **The "identical OK count" carries no information and should be struck from the item.** It reads as a control ("nothing else changed") and is not one. Under a changed check set, 78 = 78 is arithmetic coincidence.
2. **The "0 → 5" movement is, if anything, understated by the item and should be strengthened.** Because the check population grew, the correct reading is not "5 new failures appeared" but "5 failures were newly *representable*", of which at least 3 concern objects (launchd agents) that were not in the prior denominator at all. The old reading of 0 FAIL was not a false negative in the ordinary sense; it was a **frame error** — those three objects were outside the sampling frame. That is a different and more serious defect than a detector that looked and missed.

None of this touches the underlying fact. It touches the sentence the item built on it.

### Summary

The three agents at `runs = 0` are real and the diagnosis is correct. Two things the item says do not survive.

First, the headline comparison. "The OK count is identical and the FAIL count moved 0 → 5" compares 82 checks to 84 checks across a documented instrument replacement whose contract explicitly prohibits the prior instrument's enumeration method and mtime check. The denominators differ; the identical OK count is coincidence; and PREMISE-105 already forbids reading a series across a definitional change. Correctly restated, the three launchd agents were not missed by a detector — they were **outside the sampling frame**, which is a frame error and a worse defect than the item claims, so the correction strengthens the item's alarm while removing its evidence.

Second, and more consequentially, the search question's three candidate designs all fail in the same place. A positive-acknowledgement heartbeat detects a job that never begins **only if someone registered the expectation of its ping**; manifest reconciliation detects a missing job **only if the manifest lists it**; run-count polling detects `runs = 0` **only over the enumeration it was handed**. Every one of them bottoms out in an authoritative list of what ought to exist, and it was exactly that list which was wrong — `list_scheduled_tasks` returning 1 task of 70. **The instrument was not the failure; the registry was.** This is why the rebuilt check found the fault: not because run-count polling is a superior design, but because the rebuild forced a re-enumeration. The Kubernetes reconciliation literature states this boundary explicitly — drift outside the declared set produces zero signal by design — and the missing-monitor share in the Microsoft SoCC incident study (~17% of incidents lacking monitors or telemetry) is the field's measurement of the same gap.

Third, the cost side is not free and the register already knows it. Converting absence-of-complaint checks to affirmative-perishable signals is PREMISE-110's prescription and PREMISE-110's own cost caveat records 44% of organisations having an outage linked to suppressed or ignored alerts. The industry alert-fatigue numbers retrieved this run are worse than that caveat suggests — 57% of on-call teams reporting under 30% of alerts actionable, 60–80% median false-positive rates. A fleet that adds a heartbeat per scheduled object at N≈82 checks is adding 82 opportunities for a stale monitor to cry wolf, and the practitioner literature is unanimous that an **untested** dead-man's switch is worse than none because it manufactures confidence.

On the regress: it is a genuine regress under one condition and not otherwise. If each monitoring layer is the same kind of thing as the layer below — another scheduled agent, in the same runtime, reading the same filesystem — then it is PREMISE-110's single channel wearing N labels and the regress is real and unbounded. It terminates the moment one layer differs **in kind**: a hardware watchdog and its processor checking each other with mutual pulses (US4906979), or an external third-party check-in service outside the failure domain. The formulation I found puts it exactly: the regress is blocked only if detection is non-inferential and stands outside the loop it governs. That is a purchasing decision, not a design decision, and it is the one the fleet has not made.

Finally, and honestly: I searched specifically for a published detection-latency distribution for never-started scheduled jobs in production fleets and **found none**. The item's empirical half is not answered by existing literature.

### Specific risks

**Risk of accepting the item's inference as stated.** The fleet concludes that a better instrument was the missing thing, invests in a better instrument, and leaves the registry unowned. The next object added outside the enumeration — a new launchd agent, a task registered in a fourth file, a cron entry — is invisible to the new instrument for exactly the same reason the last three were invisible to the old one, and this time the failure will be harder to notice because the instrument now carries a reputation for having caught something. **PREMISE-110's inversion applies to the fix as much as to the thing fixed.**

**Risk of the two-point comparison entering the record.** "78 OK before, 78 OK after" will be cited as a control. It is not one. If it stands, every future scheduler-health reading will be compared against a baseline with a different denominator, and the fleet will have manufactured the exact series-break PREMISE-105 was minted to prevent — in the health series, which is the series where a false trend is most expensive.

**Risk of the heartbeat build.** If PREMISE-086's inverted signal is implemented per-object without registration being owned, the fleet acquires 80+ new alert sources with a documented 60–80% false-positive band and no proof-test, and PREMISE-110's cost caveat predicts the outcome: a channel with demonstrated near-zero throughput, into which the one real alert eventually arrives unread. The 44% outage-linked-to-ignored-alerts figure is the measured version of that.

**Risk of dismissing the item, recorded at full strength.** Three scheduled agents have never fired. Whatever is wrong with the item's comparison, that is a total loss of three functions for an unknown period, discovered by accident, on a fleet that already carries PREMISE-141's finding that its run model cannot represent a third terminal state. The frame error is worse than the detector error the item describes, and it is not fixed by anything in this file.

### Mitigations available

(a) **Strike the "identical OK count" clause and restate the comparison with both denominators.** 82 checks then, 84 now, different check sets, no controlled comparison available. Cheapest possible action; removes a false control from the record before it is cited.
(b) **Make the registry the artefact, not the check.** The load-bearing object is a single authoritative manifest of every scheduled thing on the machine — launchd, cron, the three registry files, anything else — with an owner and a change protocol. Every one of the three designs in the search question works once that exists and none works without it. This is the actual finding and it is not a monitoring-design question.
(c) **Add a frame-drift check, which is different from a liveness check.** Compare `launchctl list` + `crontab -l` + the registry files against the manifest, and alarm on **objects present in the world but absent from the manifest**. This is the only check in the family that could have caught the three agents *before* the rebuild, and it is a set difference, not a heartbeat.
(d) **If heartbeats are built, build them selectively and by criticality**, per PREMISE-110's own cost caveat and per SIL practice on allocating diagnostic coverage. Not 84 heartbeats. The three or four objects whose silent absence is actually expensive.
(e) **Terminate the regress by kind, not by layer.** One external check-in service outside the fleet's runtime, scheduler, credentials and filesystem — or nothing. A monitor-of-monitor implemented as another scheduled agent is PREMISE-110's single channel wearing two labels and adds no coverage.
(f) **Proof-test whatever is built,** per PREMISE-110: deliberately unload an agent in a sandbox and confirm the check turns red within the expected interval. The practitioner literature's "an untested dead man's switch is worse than none" is the same instruction.
(g) **Do not attempt to derive a detection-latency figure and publish it as a benchmark.** No published baseline exists (source 8). Per PREMISE-124 any internal figure is uncalibrated; if one is produced, it must carry a seeded denominator — deliberately disable a low-value job and measure time-to-detection — or be tagged UNCALIBRATED.

## STEELMAN

**Item:** ASSUMPTION-1086

**Strongest counterargument:** The item has the diagnosis right and the epistemology wrong, and the epistemology is what will be acted on. Its headline sentence — "the OK count is identical and the FAIL count moved 0 → 5" — reads as a controlled before-and-after and is not one: 78 + 4 + 0 is 82 checks and 78 + 1 + 5 is 84, across an instrument whose own contract, quoted in the sibling item, forbids the prior instrument's enumeration method and its mtime comparison. Two different check populations produced the same OK count by coincidence, and the register already has a premise forbidding exactly this reading (PREMISE-105, a definitional change breaks a series). Strip the false control and what remains is worse, not better: the three launchd agents were never missed by a detector, they were **outside the frame**, because the old instrument's enumeration returned 1 task of 70. That distinction is the whole finding, and the item's framing — "the ability to see them" — obscures it by locating the defect in perception rather than in the list of what exists. It matters because it determines what gets built next. Every design the search question offers fails at the same joint. A positive-acknowledgement heartbeat fires when an expected ping does not arrive, and a job that has never run has never pinged, so the alert exists only if a human separately told the monitor to expect it — which is the same registration act that was missed. Manifest reconciliation compares world to declared state and is blind by construction to anything not declared; the Kubernetes controller literature states this outright, that drift outside the owned set produces zero signal because nothing about the declared state has drifted. Run-count polling reads `runs = 0` over whatever enumeration it is handed. All three are downstream of an authoritative registry that nobody owns, and the reason the rebuilt check worked is not that run-count polling is the superior design — it is that a rebuild forces a re-enumeration. Build the best heartbeat in the world and the next unregistered object is invisible again, and this time behind an instrument with a reputation. Meanwhile the cost of the obvious remedy is measured and unfavourable: the on-call literature reports 57% of teams seeing fewer than 30% of alerts as actionable, industry-median false-positive rates of 60–80%, 83% of engineers dismissing alerts at least sometimes, and 44% of organisations suffering an outage traceable to a suppressed or ignored alert — a figure this register already carries in PREMISE-110's cost caveat. Adding eighty-odd unproven heartbeats to an eighty-four-check fleet is a plan to build the channel that eats the one real alert. And the regress is genuine, not rhetorical: a monitor-of-monitor that is another scheduled agent in the same runtime with the same credentials is PREMISE-110's single channel wearing two labels, and stacking them terminates nowhere. It terminates only when a layer differs **in kind** — a hardware watchdog exchanging check pulses with the processor it guards, or an external check-in service outside the failure domain — which is a purchase, not a design. Last, the empirical half of the item cannot currently be settled: I searched for a published detection-latency distribution for never-started scheduled jobs in production fleets and there is none. The nearest quantities are ~17% of incidents in a large cloud service lacking monitors or telemetry coverage, and 78% of organisations reporting at least one incident where no alert fired at all. On the first of those, a fleet that discovers a monitoring blind spot is **inside the industry's normal operating band**, which is not exoneration — it is the reason the finding needs a registry owner rather than an alarm.

**What would need to be true for C2A2 to be safe:** An authoritative, owned manifest of every scheduled object on the machine must exist, with a change protocol, and the primary check must be a **set difference between the world and that manifest** rather than a liveness signal over the manifest's contents. Second, any liveness layer added on top must sit outside the fleet's runtime, scheduler, credentials and filesystem — an external check-in service, not another agent — or PREMISE-110's common-mode guard voids its coverage. Third, whatever is built must be proof-tested by deliberately breaking a monitored object and confirming the alarm, because the practitioner consensus that an untested dead-man's switch is worse than none is the same instruction PREMISE-110 already gives. Fourth, the 08-05 baseline comparison must be withdrawn or restated with both denominators before it is cited again. If all four hold, the item's remedy is safe; if only the fourth is skipped, the fleet is merely carrying a bad number; if the first is skipped, nothing else in the list helps.

**How to test:** (1) **Frame audit, minutes of work, highest value.** Enumerate `launchctl list`, `crontab -l`, and all three registry files; diff against the manifest the scheduler check uses. Every object present in the world and absent from the manifest is a currently-invisible failure and the count is the item's real finding. (2) **Seeded-detection experiment**, which also supplies the missing latency number honestly: disable one low-value job without telling the instrument, record the wall-clock interval until the check reports it. Repeat for a job that fires but produces nothing, which discriminates PREMISE-141's two states. Report both as a seeded denominator per PREMISE-124. (3) **Registration-gap test for any heartbeat build:** create a new scheduled object *without* creating its heartbeat check and confirm — the expected result is silence, which is the whole point. If the heartbeat design cannot fail this test, it has an owner-of-registration and is safe. (4) **Common-mode test per PREMISE-110:** run the monitor-of-monitor and the monitored fleet, then kill the shared parent, and see whether anything reports. If nothing does, the layer is decorative.
