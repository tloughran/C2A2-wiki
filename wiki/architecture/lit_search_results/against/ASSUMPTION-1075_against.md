### Strength of challenge: Moderate-to-Strong (on framing and remedy); Weak (on "none was fixed")

### Summary

The three defects are real and defect (iii) is genuinely alarming, but the item's organising concept is doing less work than it appears to. Fail-open is not a bug class; it is a documented design choice that the literature says is correct wherever availability outranks enforcement, and the most-cited recent demonstration of the alternative — CrowdStrike's July 2024 update taking down 8.5 million machines — is what failing closed looks like when the control itself is wrong. C2A2's checks guard a research corpus, not an access boundary, and no source I found puts quality gates of that kind on the fail-closed side by default. More usefully, all three cases are misdescribed. A check that reads a field that is absent and returns success is not making a permissive decision; it is making **no decision and reporting one**. Test tooling names this and fixed it long ago by separating outcomes: pytest counts and lists skips separately from passes, and the Linux kernel selftest harness carries a patch specifically because zero-assertion tests returned 0 and read as passes. The right remedy is therefore a third state — PASS / FAIL / **NOT-RUN** — plus a count of checks actually executed, which converts "five of six pairs silently skipped" from an anecdote a run happened to notice into a number on every report. That change is cheaper than a polarity flip, it does not risk blocking the fleet on cold caches, and it is the only remedy that addresses defect (iii), where the vault's own prescribed `{"segments": [...]}` workaround removes the field the length check reads. On the item's third proposition I could not sustain a challenge. Known-error-with-documented-workaround is legitimate practice, but not when the documented workaround is what disables the control — that is a *control failure recorded as a procedure*, and Vaughan's normalisation of deviance describes exactly what happens to a flaw that is recurrently observed without consequence. The disconfirmatory search strengthened the item there, and the reconciliation should register that.

### Specific risks

If the fleet flips these checks to fail-closed, the near-term consequence is predictable from its own data: cold `/tmp` caches were hit by four independent runs in one day, so a fail-closed fidelity check would have failed four runs on an environment condition. In a fleet already losing 36% of runs to termination, adding environment-triggered hard failures is a reliability change disguised as a rigour change, and the second-order effect — a failure stream dominated by false positives, read by nobody — is the regime the alert-fatigue literature describes.

If the fleet keeps fail-open and adds nothing, defect (iii) is the live hazard and it is severe in a specific way: the length check does not merely fail to run, it fails to run **wherever the vault's own recorded workaround has been applied**, which is presumably everywhere the workaround was needed. The population where verification is silently absent is exactly the population where the input was already anomalous. No report anywhere in the fleet distinguishes those pairs from verified ones.

If the recurrence is left unaddressed, Vaughan's mechanism applies without qualification: three defects re-derived by runs that all knew they were known, none ticketed, is a rehearsal for treating them as background conditions. The item's own phrasing — "recurred unchanged from five hours ago" — is the fleet noticing the drift while it happens.

### Mitigations available

(a) **Add the third state.** Every check returns PASS, FAIL, or NOT-RUN with a reason. `fidelity_check.py` asserts its own preconditions — `raw_asr_word_count` present, sentences extractable — and reports NOT-RUN when they are absent. This is the single highest-value change in this file: it fixes all three defects, changes no polarity, blocks nothing, and makes defect (iii) impossible to reproduce silently.
(b) **Report checks-executed alongside checks-passed.** "6/6 pairs passed" and "6/6 pairs checked" are different claims and the fleet currently publishes only the first. A coverage denominator turns "five of six silently skipped" into a standing metric rather than an incidental observation.
(c) **Tamper-test the checkers.** Run each verification script against a deliberately corrupted input and confirm it fails. This is the assertion-count tamper check in the fleet's idiom, it costs one fixture per checker, and it would have caught defect (iii) before it was written into a workaround.
(d) **Reconcile the workaround with the check it disables.** Defect (iii) is not a code bug alone — a recorded procedure prescribes an input shape that removes a control. Either the workaround emits the field, or the check reads it from elsewhere, or the workaround is annotated as disabling the length check. Any of the three closes it; none is currently in place.
(e) **Ticket the known errors, with an explicit accept-decision.** The legitimate version of "not fixed" is a recorded decision to accept a known error with a stated workaround and a review date. The illegitimate version is silence. Converting these three from silence to recorded acceptance is what stops Vaughan's mechanism, and it costs three lines.
(f) **Do not flip polarity by default.** If any check is to fail closed, choose it on the argument the literature requires — what does a false pass cost here versus a false block — rather than as a class-wide rule.

### Recommendation: PARTIALLY-CHALLENGED

## STEELMAN

**Item:** ASSUMPTION-1075

**Strongest counterargument:** "Fail-open" is the wrong name for what happened, and the wrong name is steering the fleet toward a fix that would hurt it. Fail-open is a deliberate posture — the industry's own formulation is that systems should fail closed where security outranks access and fail open where availability comes first — and the most expensive recent lesson in this area runs the other way: CrowdStrike's July 2024 update failed closed at kernel level and took 8.5 million machines down with it, across aviation, banking and emergency services. A verification script on a research corpus is not an access control, and the case for making it block has to be argued, not assumed. But the deeper point is that none of these three checks is making a permissive decision at all. A check that reads `raw_asr_word_count`, finds nothing, and exits zero has not decided to allow anything; it has decided nothing and reported a decision. The testing world hit this exact wall and did not solve it by inverting polarity — pytest counts skips and xfails separately from passes, and the Linux kernel carries a patch titled "avoid false negatives if test has no `ASSERT`s" because zero-assertion tests returned 0 and looked green. The fix is a third outcome and a coverage denominator: PASS, FAIL, NOT-RUN, and a count of checks that actually executed. That would have surfaced "five of six pairs silently skipped" as a number on every report instead of a thing one run happened to notice, and — the part a polarity flip cannot do — it would have caught defect (iii), where the vault's own prescribed `{"segments": [...]}` workaround removes the field the check reads. Flipping to fail-closed, meanwhile, would have hard-failed four runs on a cold `/tmp` cache in a single day, in a fleet already losing a third of its runs, and would have produced a failure stream that nobody reads. Where the item is unimprovable is its last clause. Three defects, known to be known, re-derived independently, none ticketed, is Vaughan's mechanism running on schedule — a flaw recurrently observed without consequence becomes the norm — and no amount of arguing about polarity touches that.

**What would need to be true for C2A2 to be safe:** Each verification must be able to say *whether it ran*, and every report must carry both a pass count and a checks-executed count, so that a silent skip is arithmetically visible rather than dependent on a reader noticing. Given that, fail-open is a defensible posture and no polarity change is needed. Given a polarity change without it, the fleet gets a check that blocks on environment conditions and *still* cannot tell you whether it evaluated anything — the worst of both. And independently of either: defect (iii) must be closed at the level where it lives, which is a recorded procedure that disables a control, not a line of Python.

**How to test:** **One, and it decides the whole question:** feed each verification script an input that is definitely wrong — a truncated transcript, a mismatched word count — and see whether it fails. If it passes, the check is vacuous and no polarity setting will help. This is one fixture per checker and it needs no attendance. **Two:** count how many pairs in the last 30 days were processed through the `{"segments": [...]}` workaround. That number is the size of the population whose length check never ran, and it converts defect (iii) from a discovery into a measured exposure. **Three:** for the polarity question specifically, replay the day's runs with the checks set to fail closed and count how many would have hard-failed. If the answer is four cold-cache failures out of six pairs, the fleet has priced the remedy the item's framing implies and can decide with a number instead of an intuition.

## SYSTEMIC-RISK-FLAG

**Date:** 2026-08-15
**Affected items:** ASSUMPTION-1068, ASSUMPTION-1069, ASSUMPTION-1075, ASSUMPTION-1077 (peripherally ASSUMPTION-1070)
**Common vulnerability:** **Every instrument these four items propose draws its sample from the set of runs, artefacts or decisions that reached a recording surface — a frame generated by the very process the instrument is meant to audit.** 1075's contribution to the pattern is the sharpest: a silently skipped check removes its pair from the checked population *and* reports success, so the fleet's quality statistics are computed over exactly the pairs where verification worked. The pairs where it did not are invisible in the numerator and the denominator alike.
**Literature basis:** PCAOB **AU 350 / AS 2315** — "an auditor would **not** be able to detect understatements of an account due to **omitted items** by sampling the **recorded** items" [verified this run]. **Priest & Klein (1984)** on selection effects in adjudicated sets [verified this run, snippet level]. **pytest skip/xfail separation** and the **Linux kernel selftest zero-assertion patch** as the engineering precedent for making the unchecked population countable [verified this run].
**Risk level:** Critical
**Recommendation:** Every instrument must publish its **denominator** — for 1075 specifically, checks-executed alongside checks-passed. Without a denominator sourced independently of the check's own success, a pass rate is a statement about the checker's uptime, not about the corpus.
