  Strength of challenge: Moderate

  Summary: The general claim — that capability is a session property and that no contract names it — is well supported by the configuration-error literature and is not what the challenge targets. What is challenged is the inferential step: "the determinant of success" is a causal conclusion drawn from a univariable split of twenty-nine same-day, non-independent observations, and the Simpson's-paradox literature is explicit that no test distinguishes such an association from a confounded one without an external causal model. The obvious confound is task type: runs that need a host mount are plausibly also the longer, more I/O-heavy, more externally-dependent runs, and any of those properties could carry the association. Yin et al. further indicate that in the largest characterisation of real misconfigurations, environment/provisioning is a minority class behind parameter mistakes, so a single day's dominance is weak evidence about the pipeline's steady state. Both candidate remedies are also weaker than they appear: hermetic execution is documented to be slow and incomplete at ecosystem scale, and a contract-declared pre-flight check is a TOCTOU pattern that verifies a precondition which can change before use.

  Specific risks: If C2A2 acts on "the mount is the determinant" and adds mount declaration plus a pre-flight check, and the true driver is a confounded property (task duration, external dependency, output size), the fix will appear to work for a while — because mount-requiring runs are the affected runs — and then fail without warning when a non-mount run hits the same underlying cause. The pre-flight check itself creates a false guarantee: a session that passed the check at start can lose or change the mount before the work runs, and downstream logic that trusts the declaration will now fail more confusingly than it did when nothing was declared. Committing to hermetic execution on the strength of one day's twenty-nine runs risks a large, slow programme (the reproducible-builds evidence suggests months, and never fully complete) whose motivating measurement may not replicate. Finally, if contracts start declaring capabilities, agents will begin *reasoning from the declaration* rather than from the environment, which converts a visible failure into a silent wrong-answer failure.

  Mitigations available: Before acting, stratify — cross the mount/no-mount split with at least task type, runtime, and output size, across more than one day, and check whether the association survives (this is the Mantel-Haenszel / multivariable step the Simpson's-paradox literature prescribes). Prefer verification at point of use over pre-flight declaration, to avoid TOCTOU: have the work path itself assert the mount immediately before the operation that needs it and fail loudly. Make the assertion a positive completion record rather than a start-time check. Treat contract declaration as documentation, not as a guarantee, and never let downstream code branch on a declared capability without a use-time check. If pursuing hermeticity, scope it to the specific dependency classes the reproducible-builds work identifies as tractable (paths, locale, hostnames, timestamps) rather than as a general programme.

  STEELMAN:
    Item: PRESUMPTION-834
    Strongest counterargument: The item's finding is an association discovered by sorting one day's twenty-nine runs on a single binary and observing that it separates outcomes — and the statistical literature is unambiguous that this design cannot distinguish a cause from a confound, that there is no test which detects spuriousness from the data alone, and that univariable analysis is precisely the method that fails here. Mount-requiring runs almost certainly differ from non-mount runs in other ways — they are the ones touching the host filesystem, so probably the longer, heavier, more externally-coupled ones — and any of those could be the real driver. Twenty-nine runs on one day, sharing a host and a scheduler, are also not twenty-nine independent trials. Beyond the statistics, both remedies the item points toward are compromised: a pre-flight capability check is a textbook TOCTOU pattern that verifies a precondition which can lapse before use, and hermetic execution is shown at ecosystem scale to take months and to leave a residue of environment-dependent causes of the very kind at issue. So the item may be right that capability is a session property, while being wrong that the mount is *the* determinant, and wrong that naming it in a contract would help.
    What would need to be true for C2A2 to be safe: (a) the mount/outcome association survives stratification by task type, runtime and external dependency, over more than one day; (b) capability is verified at point of use, not at session start, so no TOCTOU window exists between declaration and reliance; (c) no downstream logic branches on a declared capability without a use-time assertion; (d) the environment-monitoring instrument's own false-positive and false-negative rates are measured, since an unreliable detector is the only kind available; (e) any hermeticity programme is scoped to dependency classes with demonstrated tractability rather than adopted wholesale on one day's evidence.
    How to test: Two steps, both cheap. First, replication and stratification: collect runs over 5–10 days, tabulate outcome by mount-requirement crossed with task type and runtime bucket, and check whether the mount effect persists within strata. If it reverses or vanishes in any stratum, the univariable finding was confounded and the item's causal claim is refuted as stated. Second, a direct intervention: take a set of mount-requiring tasks and run them with the mount deliberately present and deliberately absent, holding task and input constant. That converts the observational claim into an experimental one and settles sufficiency in a single afternoon. Additionally, run a TOCTOU probe — assert the mount at session start, sleep for the typical queue delay, then assert again — and count discrepancies; a non-zero count directly refutes pre-flight declaration as a guarantee.
