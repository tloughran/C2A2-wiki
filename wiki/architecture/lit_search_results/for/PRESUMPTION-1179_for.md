  Sources:
    1. Newman, S., 2020 (cited as 2nd ed. by Zalando; edition not verified). "Monolith to Microservices." O'Reilly. [quoted via source 2, book not read]. Quoted passage: "rather than calling either the old or the new implementation, instead we call both, allowing us to compare the results to ensure they are equivalent ... Typically, the old implementation is considered the source of truth until the ongoing verification reveals that we can trust our new implementation." Relevance: this is direct normative support for (a). The old path stays authoritative until verification shows the new path can be trusted. Creating the new path is not enough. Newman also says (same source) that a full parallel run "is typically reserved for those cases where the functionality being changed is considered to be high risk".
    2. Sabzevari, A. and Sarracco, F., 2021. "Parallel Run Pattern - A Migration Technique in Microservices Architecture." Zalando Engineering Blog, 4 Nov 2021. [fetched/read in full]. Each endpoint had a consistency threshold. "Once that threshold has been achieved, the migration can be considered safe, and we can perform the switch." Matched, unmatched and failed counters went to Prometheus/Grafana, and the switch happened per endpoint through a proxy, which made rollback easy. Relevance: this supports (a) and (b) in practice. Cutover is gated on a measured verification signal, and the signal comes from a dedicated instrument (a consistency checker plus metrics) that can see the new path's outputs. Without such an instrument the gate cannot be evaluated, which is the condition the item describes. Caveat: here the comparison runs inside the new service, so it is not fully independent of both paths.
    3. Google SRE Book (Beyer et al., 2016), dark-launch passage. [snippet only, via Goodreads reader highlights; chapter text not read]. SRE may help set up a "dark launch" in which part of existing users' traffic goes to the new service as well as to the live production service. Relevance: this is weak support that SRE practice keeps the old path live while the new one is exercised. No passage was found on verifying before decommissioning or on independence of the verifier.
    4. GitHub Scientist and its ports (Laboratory for Python; Tzientist for Node). [snippet only, package pages]. These libraries run old ("control") and new ("candidate") code, compare the results, and always return the control result. Relevance: this shows that the verify-while-old-remains-authoritative pattern is built into standard tooling. Noted limitation: the pattern is unsafe for side-effecting code such as database writes or emails. Scheduled routines that write files are side-effecting, so running both may itself cause double-processing.
    5. Progress Automate MFT user guide, "Complete the migration cutover." [snippet only]. The guide says to disable the original task, verify it cannot run automatically, and confirm that files are not being processed by both the old and new systems. Relevance: this is practitioner support that cutover is an explicit verified step for scheduled-task migrations specifically, close to the C2A2 case.
    6. Splunk Observability Cloud migration assistant, Phase 5/6 guidance. [snippet only]. Validate each wave immediately and observe it for at least 72 hours before retiring the superseded monitoring. Relevance: this is vendor support for keeping the old path until the new one is observed working, with an explicit observation window.
    7. Liberty Consulting report on FairPoint/Verizon cutover readiness, NH PUC Docket 07-011 (Exhibit Staff C-1, 2008-11-25). [snippet only]. All three states required, as a condition of approval, "careful monitoring of the cutover process ... by an independent third party." Relevance: this is the only direct support found for (c), and it comes from a regulated telecom systems cutover. It shows independent cutover verification as an institutional requirement in high-stakes migrations, not as routine software practice.

  Strength of support: Moderate

  Summary: The literature supports the core of the item. Standard migration practice (parallel run per Newman 2020, quoted; the Zalando case, read in full; Scientist-style tooling; vendor cutover guides) does not treat a migration as done when the destination exists. The old path stays authoritative and enabled until a measured verification signal shows the new path behaves correctly. Only then is the old path switched off, ideally with rollback available. That signal always comes from an instrument that can see the new path's outputs, such as a consistency checker, metrics, or an observation window. So a cutover precondition that no instrument can evaluate cannot be satisfied in principle, as the item says. The leftover local entries are consistent with the conservative half of the practice: keep the old path until verified. What is missing is the verification step and an exit criterion. On the explicit question, whether cutover verification is normally done by an observer independent of both paths, support is thin. Most practitioner patterns put the comparator in or beside the new path. Third-party independent monitoring appears as a regulatory condition in the FairPoint case, not as a general norm. The general monitoring principle that the watcher must not depend on what it watches (seen in a dead-man's-switch search for PRESUMPTION-1182) points the same way but was not found stated for migrations.

  Caveats:
    - Newman is read only through the Zalando quotation. The edition and year are as Zalando cites them.
    - The Google SRE Book was not read. The dark-launch passage is a reader highlight. No SRE Book text was found on verify-before-decommission or on verifier independence, so the item's suggested anchor ("SRE Book chapter on change management") is not confirmed by this search.
    - Most sources are practitioner or vendor material, not peer-reviewed.
    - The patterns found concern request/response services. A scheduled routine has no live request to mirror, so the C2A2 equivalent is checking for evidence of execution (output artefacts, run logs), which these sources do not address.
    - Leaving both paths enabled is not obviously wrong. Scientist-style guidance warns that running side-effecting code twice is hazardous, so a month of dual-running may itself have risked double writes. That is a separate hazard from the one the item names.
    - "Independent of both paths" may be stronger than the literature requires. The common standard is "independent of the old path and able to see the new one's outputs".

  Recommendation: PARTIALLY-SUPPORTED

    Implication: There is a small configuration-level contribution: an explicit "unverifiable cutover" state for migrations whose destination cannot be observed, with a defined indirect-evidence check (for example, the cloud run's output artefact appearing in the vault within the expected window) as the gating signal.
